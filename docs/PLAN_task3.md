# План разработки интеграционных тестов ghreport

Дата: 2026-10-25.

Статус: план согласован в диалоге, включая уточнение критерия переноса Go-тестов,
вложенную структуру набора и отказ от общего внутреннего бюджета времени.
Этапы 1–4 реализованы и проверены на Windows и Linux. Результаты live-группы
получены на временных совместимых API с разной выдачей; отдельного API
пользователь не предоставлял.

### Выполнение этапа 1

Созданы общий запускатель через GHREPORT_BIN, отдельные фикстуры и временные
каталоги каждого теста, многопоточный локальный HTTP-сервер с журналом запросов
и очисткой, независимые проверки JSON/схемы/RFC3339, requirements и начальный README.
Live-набор и сложные HTTP-сценарии следующих этапов пока не создавались.

В mock-наборе 15 случаев: девять ошибок конфигурации и шесть сочетаний
назначения отчёта с вариантами base URL и токена. Проверяются запрос, точные
данные отчёта, Unicode, labels, сохранение created_at, generated_at, файловый
вывод и отсутствие побочных действий при ошибках аргументов. Процесс получает
только явно выбранные API-настройки; отдельный прогон с унаследованными ложными
URL/токеном подтвердил изоляцию mock-сценариев.

После успешных Python-прогонов на обеих ОС удалены три заменённые Go-проверки:

### Выполнение этапа 3

Добавлены test_cache.py (семь случаев), test_redirects.py (11), test_retries.py
(пять) и 12 случаев в test_files.py. Всего в mock-наборе 74 случая. Live-набор
не создавался. Рабочий Go-код, Dockerfile и зависимости не менялись.

Проверены кэш между отдельными процессами, слабые и обычные ETag, 304 без Link,
обновление и сохранение метаданных по 304, сброс ETag/Link по 200, постоянный 301,
изменение limit/since на исходных страницах, повреждённые JSON/ETag и отсутствие
устаревшего успешного отчёта после отказа API. Сохранность прежнего тела/ETag
подтверждается последующим настоящим условным запросом и прежним отчётом по 304;
побайтовое неизменное представление JSON кэша не требуется.

Для повторов проверены реальный Retry-After: 1, исчерпание 403/429 с нулевой
серверной паузой, восстановление после 500 и обрыва тела, исчерпание 503 с тремя
настоящими паузами 1/2/4. Каждый тест имеет конечный timeout; для исчерпания 5xx
выбрано 15 секунд. Длинные паузы, таймауты и смешанные счётчики остались в Go
с подменами часов, транспорта и ожидания.

HTTP-сервер допускает явный Content-Length для детерминированного обрыва тела.
Добавлен счётчик наблюдаемого перекрытия подготовки ответов; это сохраняет
проверку последовательности соответствующих старых HTTP-сценариев и не является
формальным доказательством отсутствия любой возможной параллельности.
Событий и произвольных sleep для обычных обработчиков не добавлялось.
Фикстура read_trace связывает общий проверяющий помощник с файлом текущего запуска
и срезом журнала сервера; прежние строки/попытки не могут незаметно добавляться.

## 2. Основные решения

- Служба проверяется как чёрный ящик через абсолютный `GHREPORT_BIN`.
- Набор разделяется на управляемые локальные HTTP-сценарии (`mock`) и проверки
  свойств предоставленного API с неизвестными данными (`live`).
- Достаточно Python не ниже 3.10, pytest не ниже 7 и стандартной библиотеки.
  GitHub SDK, сторонний HTTP-клиент и дополнительные pytest-плагины не нужны.
- Каждый тест имеет собственный временный рабочий каталог и кэш. Несколько
  запусков с общим кэшем разрешены внутри одного теста, а не между тестами.
- Нет зависимости от порядка запуска, настоящего токена для mock-сценариев,
  фиксированных данных GitHub или произвольных задержек синхронизации.
- Время каждого процесса и ожиданий ресурсов ограничено. Собственный механизм
  общего девятиминутного бюджета и запрета последующих запусков не создаётся.
- Проверка Docker-образа остаётся самостоятельной проверкой поставки части 2.
  Python-набор не заменяет интерфейс `GHREPORT_BIN` командой `docker run`.

## 4. Запуск службы и изоляция

Сессионная фикстура проверяет наличие `GHREPORT_BIN`, абсолютность пути и
существование файла. Ошибка настройки или запуска объясняется явно; непригодный
бинарник не заменяется другой программой. Сборка выполняется перед pytest,
без скрытого `go build`, `go run` или Docker внутри запускателя.

Общий помощник запуска:

- передаёт аргументы списком, без PowerShell/Bash и `shell=True`;
- задаёт временный `cwd` и путь к собственному кэшу теста;
- допускает несколько последовательных запусков внутри одного сценария;
- получает base URL и токен явно, не изменяя глобальный `os.environ`;
- захватывает stdout/stderr и возвращает код завершения, вывод и границы времени;
- не объявляет любой ненулевой код ошибкой помощника: ожидаемый код проверяет тест;
- ограничивает ожидание процесса и при таймауте завершает его и дожидается выхода;
- проверяет вывод как UTF-8 без молчаливой замены повреждённых символов;
- не раскрывает токен через сообщения самого тестового помощника.

Mock-запуск получает адрес своего локального сервера и синтетический токен либо
отсутствующую переменную токена. Настоящие API-настройки пользователя туда не
передаются. Live-запуск использует заданные `GITHUB_API_BASE_URL` и необязательный
`GITHUB_TOKEN`. Системные переменные, необходимые для запуска процесса на Windows
и Linux, сохраняются. Отсутствующий и пустой токен проверяются без случайного
наследования настоящего секрета.

Сами тесты не устанавливают зависимости и не загружают образы во время прогона.

## 5. Управляемый HTTP-сервер

Используется `ThreadingHTTPServer` на `127.0.0.1` с портом, назначенным ОС.
Сокет привязывается до возврата фикстуры. Сервер не должен сам навязывать службе
последовательность запросов, как это делал бы однопоточный обработчик.

Обычному сценарию достаточно обработчика, счётчика обращений и журнала.
Универсальный язык сценариев и система событий для каждого ответа не создаются.
События применяются только для согласования действий потоков, например при
вмешательстве в файловую систему во время ответа или управлении незавершённым телом.

Журнал хранит метод, исходный путь с query, необходимые заголовки, порядок
обращений и монотонные отметки времени. Общие данные защищаются от гонок.
Для обязательных параметров первого запроса сравниваются разобранные значения,
а не порядок query. Непрозрачный query адреса из Link проверяется без переписывания.

Ошибки обработчика передаются в основной поток теста. Неожиданный запрос
немедленно фиксируется и получает ответ, не провоцирующий долгую цепочку повторов.
После процесса проверяются и лишние, и недостающие обращения. Сервер не исправляет
ошибочный запрос и не возвращает успешный ответ по умолчанию.

Проверка реального `Retry-After: 1` использует разницу монотонных отметок на сервере.
Внешний процесс не получает ускоренную тестовую политику ожидания.
Счётчик активных обработчиков может обнаруживать наблюдаемое перекрытие, но сам
по себе не доказывает отсутствие любой возможной параллельности.

Очистка выполняется и после ошибки: освобождение ожидающих обработчиков,
остановка сервера, закрытие сокетов и ожидание потоков. Сокеты, события и ожидания
завершения имеют конечные пределы. Неудачная очистка не скрывается; произвольные
`sleep` для готовности и синхронизации не используются.

| Время | generated_at и ts — UTC/RFC3339; generated_at соответствует времени запуска с учётом точности; сортировка и since сравнивают моменты времени, включая смещения и дроби. |
| Пагинация и limit | Несколько страниц, rel=next, абсолютные/относительные ссылки, непрозрачный query, короткая и пустая промежуточная страница; ровно limit при достаточной выдаче; отсутствие обращения после достижения limit. |
| Фильтры и дедупликация | PR с объектом и null, исключение PR до проверки полей issue; граница since включительно в UTC; первая подходящая версия повторного number; одинаковые номера разных репозиториев независимы. |
| Порядок | Сортировка issues по времени и number; порядок репозиториев после удаления дубликатов аргумента. Выбор первых N подходящих записей при обходе соответствует согласованному алгоритму службы. |
| Коды завершения | 0 при полном успехе, 1 при частичном, 2 при ошибках аргументов, 3 при unauthorized/all_failed и согласованных локальных фатальных отказах. |
| Ошибки API | 401 немедленно прекращает запуск; 404 даёт not_found; повреждённый JSON — invalid_response; обычные 403/422 без повторов; ошибка следующей страницы отбрасывает накопленный результат репозитория. |
| Trace | Одна JSON-строка на фактическую HTTP-попытку; ts, method, url, status, attempt, from_cache, error; порядок, перенаправления и повторы; перезапись при новом запуске; отсутствие Authorization и токена. |
| Кэш | Отдельные процессы, 200 → 304, точные If-None-Match, слабый ETag, 304 без Link, равенство всего отчёта кроме generated_at; исходные страницы пригодны для другого limit/since. |
| Обновление кэша | Новый ETag/Link по 304, сохранение обновлённых метаданных при их отсутствии; новое тело по 200, удаление старого валидатора/Link при их отсутствии; необоснованный 304 отвергается. |
| Повторы | Успех после 429 с реальной паузой; конечное исчерпание rate limit с Retry-After: 0; восстановление и исчерпание 5xx; восстановление после обрыва тела с сохранением полученного HTTP-статуса в trace. |
| Перенаправления | 301/302/307, относительный Location и Link от конечного URL; постоянный 301 между процессами, временные 302/307; валидатор не переходит на другой URL; циклы и непригодный Location. |
| Файлы | stdout и файловый out; чистые потоки; фатальный JSON в stdout при файловом out, сохранение прежнего отчёта; переносимые ошибки открытия и конфликты путей. |
| Секрет | Отсутствие токена в stdout/stderr/trace/кэше; при отражении в отчёте отмена всего вывода, код 3 и сохранение старого файла, включая результат из кэша по 304. |

Общие проверки требуют обязательные поля и разрешённые типы/значения, не закрепляя
порядок JSON-ключей, порядок query первого запроса, точный текст диагностики или
не предусмотренный ТЗ запрет дополнительных безопасных полей. Для целочисленных
полей Python `bool` не принимается за число. Разбор времени совместим с Python
3.10, учитывает Z, смещения и дробную точность; строки не сравниваются лексически.

Примеры Б.1–Б.4 проверяются по смыслу: схема и отображение полей, пустой результат
ошибочного репозитория, trace 200/304, повторное использование кэша и точные
фатальные объекты. Сокращённый URL в Б.2 не отменяет параметры из 4.4.1.

## 7. Live-набор и границы проверяемости

### 7.1. Настройки и свойства результата

Репозитории задаются параметром pytest `--api-repos owner/repo[,owner/repo...]`.
Это настройка тестов, а не новая переменная или параметр службы. По одному
base URL нельзя определить доступный owner/repo; дополнительные эндпоинты
обнаружения репозиториев и фиксированный `stub/alpha` для произвольного API
не вводятся. Оператор выбирает доступные репозитории; непустая выдача не требуется.

Если обе live-настройки отсутствуют, live-группа явно пропускается; это не полный
приёмочный прогон. Частично заданная или некорректная настройка даёт понятную
ошибку подготовки. Полная приёмка включает URL, список и успешную live-проверку.
Сетевые ошибки, неподходящие credentials и ошибки API не маскируются успешным
пропуском. Возврата к публичному GitHub при отсутствии/ошибке настройки нет.

Начальный состав live-группы — два независимых запуска с небольшим limit:
общий контракт результата и результат с заданным since. Каждый тест имеет свой
кэш. Фиксируется небольшое число запусков, а не число HTTP-страниц неизвестного
сервера. Проверяются схема, типы, порядок репозиториев, count <= limit,
count == len(issues), уникальность номеров, сортировка, since, trace и безопасность.

Не предполагаются конкретные issue, их количество, наличие PR, страниц, labels
или ненулевого результата. Не требуются отношения между снимками разных запусков.
Нет обязательного 304 или равенства меняющихся отчётов. Полноценный второй клиент,
обходящий всю выдачу для сравнения нестабильных снимков, не разрабатывается.
Ссылки html_url из отчёта не открываются.

### 7.2. Сеть

Тесты выполняют только чтение. Mock-сценарии используют свой локальный сервер;
live-сценарии — явно заданный API. Рабочая трактовка сетевой границы — настроенный
origin (схема, host, порт), с допустимыми путями из Link/Location, а не буквальный
префикс пути base URL. Проверки переходов между origin остаются в Go.

Согласие по неоднозначностям получено в общих чертах. Деталь внешнего Link/Location
сохраняет ограничение: служба по согласованному контракту может следовать на другой
origin без токена. Проверка trace после запуска обнаруживает такое обращение,
но не предотвращает его. Поэтому план не обещает сетевую изоляцию по одному trace,
не вводит скрытый прокси/шлюз и не меняет поведение службы. Если предоставленный
API требует внешний переход, противоречие с сетевым ограничением сообщается
отдельно; такой переход не объявляется автоматически разрешённым. Способ его
проверки или ограничения требует уточнения перед зависимой работой.

### 7.3. Неполная информация и время

Ровно limit проверяется только на достаточной подготовленной выдаче; для
неизвестного API универсально count <= limit. Строгий кэш-сценарий 5.3.4 и Б.3
обеспечивает mock-сервер. На меняющемся API 200 вместо 304 допустим.

PR без pull_request неотличим от обычного issue с теми же полями. По неизвестной
выдаче также нельзя доказать скрытый пропуск элемента или отсутствующую следующую
страницу без Link. Полнота и исключение известных PR проверяются по эталонным
mock-данным. Служба не обязана угадывать отсутствующую информацию; отсутствие
поля pull_request в самом отчёте не доказывает правильную фильтрацию.
Повреждённый JSON и необоснованный 304 наблюдаемы и проверяются как ошибки.

Произвольный Retry-After или множество страниц без подходящих issue могут
превысить время прогона даже у совместимого API. Ограничение процесса завершается
явной ошибкой по таймауту; паузы службы не сокращаются и зависание не пропускается.

## 8. Перенос Go-тестов

### 8.1. Критерий и порядок

Единица переноса — существенное утверждение, а не имя файла, префикс TestCache
или прямой вызов Go-функции. Для каждого утверждения оцениваются уникальность,
простота внешнего воспроизведения, длительность и польза внутренней подмены.
Не требуется переносить всё технически возможное или сохранять все прямые вызовы.

Перед удалением фиксируется соответствие «исходный тест/утверждение → конкретный
Python-тест либо сохранённый Go-тест». Python-эквивалент сначала выполняется,
проверяется сохранность утверждений и нужные платформы. Временное дублирование
разрешено на период проверки; одинаковые интеграционные наборы на двух языках
постоянно не поддерживаются. Пересекающиеся сценарии объединяются без потери
уникальных регрессий. Проверки не ослабляются ради прохождения.

### 8.4. Подготовка состояния без внутренних функций

Обновление Link в `TestConditionalPageUpdates` должно быть наблюдаемо через обход,
а не только через If-None-Match: получить страницу с исходными метаданными, затем
304 с новыми ETag/Link, затем 304 без них и перейти именно по новому Link. После
200 без ETag/Link убедиться, что старый валидатор и старая страница не используются.
Limit в промежуточных запусках позволяет управлять моментом обхода без чтения кэша.

Для проверки валидаторов redirect сначала обычным запуском создать страницу
исходного URL с ETag, затем вернуть 301 и ответ цели с другим ETag. Простой сценарий
первоначального 301 не заменяет эту проверку.

Для токена в данных по 304 подготовить кэш обычным запуском без токена, затем
запустить с токеном, содержащимся в сохранённых данных. Для повреждённого ETag
необходим доступ к документированному формату кэша; эту зависимость локализовать
в регрессионном сценарии, не превращая её в общую архитектуру проверок.

Три свежие регрессии сохраняются обязательно: корректное сравнение out/trace
при symlink/..; отмена всего отчёта при токене с сохранением прежнего файла;
повреждённый ETag как промах кэша без бесполезных повторов.

### 8.5. Новое внешнее покрытие и очистка помощников

По сравнению с текущим TestCLI добавляются внешние проверки пустой промежуточной
страницы, цикла/ранней остановки, необоснованного 304, обновления метаданных,
обычных redirect-отказов, 5xx и обрыва тела, независимости одинаковых номеров между
репозиториями и свойств неизвестного API. Существующие прямые Go-проверки служат
источником существенных утверждений, но ожидаемое поведение выводится из ТЗ
и уже согласованных решений, а не копируется без проверки.

Общие Go-помощники удаляются только после проверки оставшихся ссылок.
`main_test.go` нельзя удалить целиком: там TestOutputFailures. `testTempDir` нужен
оставшимся тестам, `parseTrace` — модульным и Docker-проверкам. Удаление общей
сборки TestCLI и process-помощников допустимо после переноса всех их пользователей.

## 9. Этапы и контрольные точки коммитов

Каждый тематический этап пересматривает все относящиеся к нему Go-проверки,
не только TestCLI. После работающего Python-эквивалента и проверки утверждений
на нужных платформах удаляется заменённый сценарий. Результаты записываются здесь.
Коммиты во всех контрольных точках создаёт пользователь.

### Этап 1. План и инфраструктура, CLI и отчёт

Зафиксировать согласованный план. После отдельного разрешения реализации создать
помощники, фикстуры, локальный сервер, требования и начальный README; проверки
аргументов, запросов, схемы и stdout/файла. Проверить timeout и очистку ресурсов,
в том числе после ошибки проверки; не создавать зеркальных тестов инфраструктуры.

Готовность: соответствующие Python-проверки проходят, общий запускатель используется
везде, нет настоящей сети/секрета в mock-группе, определены владельцы перенесённых
утверждений. Перед удалением Go-эквивалентов выполнена и нужная Linux-проверка.
Контрольная точка: основа Python-набора, CLI и отчёт.

### Этап 2. Сбор, пагинация, фильтры и ошибки

Перенести collection/error-сценарии и соответствующие прямые Go-проверки; добавить
пустую промежуточную страницу, цикл/раннюю остановку, необоснованный 304 и независимые
номера репозиториев. Проверить все коды и контрольные фатальные объекты.

Готовность: точные результаты и последовательности обращений, нет пропущенных
утверждений, заменённые Go-дубликаты удалены после проверок.
Контрольная точка: сбор и ошибки API.

### Этап 3. Кэш, повторы, redirect, trace и файловые регрессии

Перенести оставшиеся процессные сценарии и выбранные прямые HTTP-проверки;
обновление ETag/Link, валидаторы redirect, исчерпание/восстановление, безопасный
вывод и файловые отказы. Сохранить узкие Go-проверки подменённых ошибок.

Готовность: работа между процессами, реальная пауза 429, точный trace, все три
свежие регрессии; Linux symlink/.. выполнен без пропуска. Проверены оставшиеся
ссылки на Go-помощники, нет постоянного двойного интеграционного набора.
Контрольная точка: кэш и отказоустойчивость, завершённый перенос mock-сценариев.

### Этап 4. Live-набор, документация и полная приёмка

Реализовать два независимых live-сценария и согласованные настройки/пропуски.
Воспроизводимо проверить группу также на управляемом совместимом API с данными,
не зашитыми в ожидания live-тестов; не вводить обязательный новый сервис окружения.
Закончить api_tests/README и относящиеся к тестам разделы README службы/корня,
включая новые команды после удаления TestCLI. Время/ИИ-инструменты не заполнять.

Готовность: пункты 5.3 и примеры Б сопоставлены с тестами; Windows и Linux проходят,
минимум Python 3.10/pytest 7 проверен; полный прогон измерен и укладывается в
10 минут. Mock-группа не требует live-настроек, Docker или публичного GitHub.
Полная приёмка live-группы не подменяется её пропуском.
Контрольная точка: часть 3 и документация.

## 10. Время, Windows и Linux

Для обычных mock-процессов выбираются короткие таймауты, для реальных повторов —
обоснованно увеличенные. Для live-процесса ориентир — 120 секунд. Нет общего
счётчика оставшегося времени, влияющего на результат последующих тестов.
Полный прогон измеряется через durations и внешнее измерение; при необходимости
весь pytest ограничивается снаружи. Успешная измеренная длительность и внешний
предел зависшего прогона — разные проверки.

Разработка выполняется на Windows с `.exe`, переносимыми путями и закрытием
файлов до очистки. POSIX-сценарий symlink/.. явно выделяется; его пропуск на Windows
не считается Linux-проверкой. Логика путей теста не должна нормализовать исходный
symlink/.. до передачи службе и тем самым скрывать регрессию.

Linux-приёмка запускает pytest и настоящий Linux-бинарник в одном тестовом
контейнере. `GHREPORT_BIN` указывает на файл внутри него. Mock-прогон выполняется
с `--network none`; зависимости и образы готовятся заранее. Live-прогон выполняется
отдельно с доступом к предоставленному API. Производственный Dockerfile службы
ради тестового Python-окружения не меняется; тестовая среда подготовки не становится
требованием обычного запуска pytest.

Проверка финального образа через существующий TestDockerImage остаётся отдельной.
Её успех не заменяет Python-прогон через GHREPORT_BIN и наоборот.

## 11. Команды проверки после реализации

Из корня репозитория в PowerShell; зависимости желательно устанавливать в заранее
выбранное виртуальное окружение:

```powershell
go -C service build -o "$env:TEMP\ghreport.exe" .
$env:GHREPORT_BIN = Join-Path $env:TEMP 'ghreport.exe'
python -m pip install -r api_tests/requirements.txt
python -m pytest api_tests/mock -q
```

Live-проверка с предоставленными значениями (токен необязателен и задаётся отдельно
в окружении, без записи в документацию):

```powershell
$env:GITHUB_API_BASE_URL = '<URL предоставленного API>'
python -m pytest api_tests/live -q --api-repos '<owner/repo[,owner/repo...]>'
python -m pytest api_tests -q --api-repos '<owner/repo[,owner/repo...]>' --durations=10
```

При подготовленном полном окружении поддерживается и команда из ТЗ
`pytest api_tests -q --api-repos owner/repo`; запуск через `python -m pytest`
позволяет явно выбрать используемый интерпретатор.

После изменения Go-тестов:

```powershell
go -C service test -count=1 ./...
go -C service vet ./...
gofmt -l service
git diff --check
```

В Linux после подготовки бинарника и зависимостей:

```bash
export GHREPORT_BIN=/absolute/path/to/ghreport
python -m pytest api_tests/mock -q
# При заданном GITHUB_API_BASE_URL и доступном репозитории:
python -m pytest api_tests/live -q --api-repos owner/repo
python -m pytest api_tests -q --api-repos owner/repo --durations=10
```

Конкретные команды подготовки тестового контейнера и его фактически проверенные
версии записываются в README по результатам реализации. Новые результаты прогонов
не объявляются до выполнения; текущий план не является отчётом о готовых тестах.
