# 1. Общие сведения

Задание состоит из трёх частей. Часть 1 - библиотека на C++ для преобразования разметки сообщений в пару «чистый текст и стилевые диапазоны». Результат работы - один git-репозиторий, содержащий все три части; состав и структура сдачи приведены в разделе 6.

Репозиторий разместить на github

Ожидаемые компетенции:

- уверенное владение C++ (стандартная библиотека, сборка через CMake, тесты);

- разработка консольных служб на Go: HTTP-клиент, обработка ошибок, тесты;

- написание автоматических тестов на Python (pytest);

- базовые навыки работы в Linux и с Docker;

- свободное чтение англоязычной технической документации (части 2 и 3 опираются на документацию GitHub REST API).

# Часть 2. Служба ghreport (Go, Docker)

## 4.1. Назначение

Служба ghreport формирует сводку по открытым issue указанных репозиториев GitHub. Сводка предназначена для регулярного обзора, поэтому служба обязана корректно работать с постраничной выдачей, условными запросами, ограничениями частоты запросов и сбоями отдельных репозиториев.

## 4.2. Синтаксис командной строки

```text
ghreport --repos <owner/repo[,owner/repo...]>
         [--limit <N>] [--since <YYYY-MM-DD>]
         [--out <file|->] [--trace <file>] [--cache-dir <dir>]
```

| Параметр | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `--repos` | строка | не задано | Обязательный список репозиториев через запятую в формате owner/repo; дубликаты удаляются с сохранением первого вхождения |
| `--limit` | целое | 100 | Максимум issue на репозиторий; значение не меньше 1 |
| `--since` | дата | не задано | Включаются issue, созданные не раньше указанной даты (00:00:00 UTC) |
| `--out` | путь | `-` | Файл отчёта; значение `-` означает стандартный вывод |
| `--trace` | путь | не задано | Файл журнала HTTP-обмена (JSON Lines); при отсутствии журнал не ведётся |
| `--cache-dir` | путь | `./ghreport-cache` | Каталог кэша; создаётся автоматически |

При некорректных аргументах выводится сообщение в stderr, стандартный вывод остаётся пустым, код возврата - 2.

## 4.3. Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `GITHUB_TOKEN` | Необязательный токен GitHub; передаётся в заголовке Authorization: Bearer; работа без токена допустима |
| `GITHUB_API_BASE_URL` | Базовый адрес API; по умолчанию https://api.github.com; завершающий слеш допускается |

Адрес API и токен читаются из окружения процесса: они не встраиваются ни в код, ни в образ. Если переменная GITHUB_API_BASE_URL не задана, используется адрес по умолчанию; если задана - служба обязана обращаться именно по указанному адресу, в том числе при запуске в контейнере.

## 4.4. Обмен с API

Служба обращается к единственному эндпоинту - списку issue репозитория. Все запросы выполняются последовательно, без параллельных обращений.

### 4.4.1. Формирование запроса

Метод и путь: GET {base}/repos/{owner}/{repo}/issues.

Параметры строки запроса: state=open, sort=created, direction=asc, per_page=100.

Заголовки: Accept: application/vnd.github+json; User-Agent с осмысленным значением (описывается в README); X-GitHub-Api-Version: 2026-03-10; Authorization: Bearer `<token>` при наличии токена.

Перенаправления 301, 302, 307 обрабатываются по документации GitHub.

Таймаут одного запроса - не более 30 секунд.

Пример адреса первого запроса (для наглядности разделён на две строки):

```http
GET https://api.github.com/repos/cli/cli/issues
    ?state=open&sort=created&direction=asc&per_page=100
```

### 4.4.2. Постраничная выдача

Адрес следующей страницы берётся из заголовка Link ответа, из части rel="next"; адреса страниц вручную не конструируются.

Порядок работы: запросить очередную страницу; включить подходящие элементы; если набрано limit элементов или части next нет - остановиться; иначе перейти по адресу из Link и повторить.

Порядок элементов сохраняется: по возрастанию created_at, затем по number.

Пример заголовка Link (адреса сокращены):

```http
link: <...?per_page=100&page=2>; rel="next", <...?per_page=100&page=7>; rel="last"
```

### 4.4.3. Фильтрация и дедупликация

Из элементов исключаются pull request-ы: признак - наличие ключа pull_request.

При заданном --since исключаются элементы с created_at меньше начала указанной даты (UTC). Фильтр выполняется службой: параметр since API не используется, так как он фильтрует по дате обновления, а не создания.

Элементы с одинаковым number включаются в отчёт один раз: если запись встречается на нескольких страницах, служба устраняет повтор дедупликацией.

### 4.4.4. Кэширование

Для каждого адреса служба сохраняет заголовок ETag и тело успешного ответа в каталоге --cache-dir.

При повторном запросе того же адреса отправляется заголовок If-None-Match с сохранённым значением.

Ответ 304 Not Modified: тело берётся из кэша, в журнал записывается from_cache: true.

Ответ 200: кэш обновляется, в журнал записывается from_cache: false.

Кэш переживает перезапуски процесса и не содержит токен.

### 4.4.5. Ограничения частоты и повторные попытки

Признаки исчерпания лимита: коды 403 или 429; при этом в теле сообщается об исчерпании лимита, либо присутствует заголовок retry-after, либо x-ratelimit-remaining равен нулю.

Пауза перед повтором: по значению retry-after; иначе - до времени x-ratelimit-reset (UTC, epoch); иначе - не менее 60 секунд.

При исчерпании лимита можно самостоятельно выбрать разумный конечный лимит повторных попыток; выбранный лимит описывается в README.

Сетевые ошибки и ответы 5xx: до трёх повторных попыток на запрос с задержками 1, 2 и 4 секунды.

После исчерпания повторов репозиторий получает код ошибки, обработка переходит к следующему репозиторию.

### 4.4.6. Ошибки и коды возврата

| Код | Ситуация | Вывод |
| --- | --- | --- |
| 0 | Все репозитории обработаны успешно | Отчёт |
| 1 | Часть репозиториев завершилась с ошибкой | Отчёт; у проблемных репозиториев заполнено поле error |
| 2 | Некорректные аргументы | Сообщение в stderr |
| 3 | Фатальная ошибка: ответ 401 или все репозитории с ошибками | `{"error": "unauthorized"}` или `{"error": "all_failed"}` в stdout |

Коды ошибок репозитория: not_found (ответ 404), rate_limited (исчерпание лимита), request_failed (сетевые ошибки или 5xx после повторов), invalid_response (ответ не является корректным JSON).

## 4.5. Формат отчёта

Отчёт - один JSON-объект UTF-8 следующей схемы:

```text
{
  "generated_at": "<UTC, RFC3339>",
  "repos": [
    {
      "repo": "<owner/repo>",
      "error": <null | "not_found" | "rate_limited" |
                         "request_failed" | "invalid_response">,
      "count": <целое число>,
      "issues": [
        {
          "number": <целое число>,
          "title": "<строка>",
          "author": "<login>",
          "labels": ["<строка>", ...],
          "created_at": "<RFC3339, как в ответе API>",
          "url": "<html_url>"
        }
      ]
    }
  ]
}
```

Порядок репозиториев - как в аргументе --repos.

Массив issues отсортирован по created_at, затем по number (возрастание); count равен длине массива.

Поле error равно null при успешной обработке репозитория.

Соответствие полей отчёта полям ответа API:

| Поле отчёта | Источник |
| --- | --- |
| Number | `number` |
| Title | `title` |
| Author | `user.login` |
| Labels | `labels[].name`, в порядке ответа |
| created_at | `created_at` |
| url | `html_url` |
| Count | вычисляется |
| generated_at | текущее время UTC |

## 4.6. Журнал (--trace)

Формат JSON Lines: одна строка на каждую попытку HTTP-запроса, в порядке выполнения.

Поля записи: ts (RFC3339, UTC), method, url (полный адрес), status (код ответа; 0 при отсутствии ответа), attempt (номер попытки, начиная с 1), from_cache (истина при использовании данных кэша по ответу 304), error (null или краткое описание, например timeout или network).

Заголовок Authorization в журнал не записывается.

## 4.7. Стандартный вывод и журналирование

В стандартный вывод попадает только отчёт либо фатальный JSON-объект; диагностика направляется в стандартный поток ошибок.

Токен не попадает ни в stdout, ни в stderr, ни в журнал.

## 4.8. Контейнеризация

В каталоге service/ размещаются Dockerfile и .dockerignore.

Сборка и запуск: docker build -t ghreport service/; docker run --rm -e GITHUB_TOKEN=... ghreport --repos cli/cli --limit 20 --out -.

Переменные окружения передаются контейнеру при каждом запуске (флаг -e) и не вшиваются в образ. В примере указан только токен: GITHUB_API_BASE_URL не задан, потому что по умолчанию используется публичный адрес https://api.github.com. При работе с другим сервером, совместимым с контрактом, адрес передаётся тем же способом, например: docker run --rm -e GITHUB_TOKEN=... -e GITHUB_API_BASE_URL=<адрес сервера> ghreport --repos cli/cli --out -.

Контейнер запускается от непривилегированного пользователя (инструкция USER); секреты в образ не вшиваются; служба не зависит от файлов на хосте.

# 5. Часть 3. Интеграционные тесты службы (Python)

## 5.1. Цель

Требуется набор тестов на pytest, который проверяет службу ghreport как чёрный ящик: запускает её как отдельный процесс и проверяет наблюдаемое поведение - содержимое отчёта, журнал и коды возврата.

| Переменная | Назначение |
| --- | --- |
| `GHREPORT_BIN` | Абсолютный путь к собранной службе ghreport |
| `GITHUB_API_BASE_URL` | Базовый адрес сервера, совместимого с контрактом из части 2 |
| `GITHUB_TOKEN` | Необязательный токен; может отсутствовать |

Набор включает два сценария: детерминированные интеграционные тесты с локальным mock HTTP-сервером с управляемыми ответами и тесты с API по адресу GITHUB_API_BASE_URL, где состав выдачи заранее неизвестен. Mock-тесты воспроизводят предусмотренные HTTP-сценарии, включая 429, 304 и постраничную выдачу; тесты с API проверяют свойства результата независимо от конкретных данных. В обоих сценариях ghreport запускается как отдельный процесс; для mock-тестов GITHUB_API_BASE_URL указывает на локальный сервер.

- Тесты с API обязаны работать с любым сервером, соответствующим контракту: состав выдачи, количество страниц и значения полей заранее неизвестны.

- Тесты не обращаются в сеть вне GITHUB_API_BASE_URL и не изменяют состояние репозиториев: только чтение.

- Каждый тест использует собственный временный каталог кэша.

## 5.3. Требования к покрытию

1.  Постраничная выдача и --limit: при выдаче в несколько страниц в отчёт попадает ровно limit подходящих элементов, повторов по number нет.

2.  Фильтрация pull request-ов: элементы с признаком pull_request в отчёте отсутствуют.

3.  Фильтр --since: в отчёт попадают только issue, созданные не раньше указанной даты.

4.  Кэширование: повторный запуск с тем же каталогом кэша приводит к записям from_cache: true в журнале и к отчёту, совпадающему с первым запуском по всем полям, кроме generated_at.

5.  Ограничение частоты: при ответе 429 с заголовком retry-after служба выдерживает паузу и завершает работу успешно.

6.  Ошибки: ответ 401 приводит к фатальному завершению с кодом 3, ответ 404 по одному из репозиториев - к отчёту с кодом 1 и полем error у этого репозитория.

7.  Схема отчёта: обязательные поля, их типы, сортировка issue по created_at, затем по number.

8.  Журнал --trace: набор полей записи и отсутствие заголовка Authorization.

## 5.4. Требования к качеству набора

Детерминированность: отсутствуют произвольные задержки; ожидание результатов ограничено по времени.

Независимость: тесты не зависят от порядка запуска и друг от друга.

Полный прогон занимает не более 10 минут.

Набор должен обнаруживать нарушения контракта, а не только подтверждать успешный сценарий. Примеры нарушений: пропуск элемента при постраничной выдаче; pull request без признака pull_request; ответ 304 на запрос без If-None-Match; повреждённый JSON; неверное направление сортировки; отсутствие заголовка Link при наличии следующей страницы.

## 5.5. Пример организации набора

conftest.py готовит функцию запуска службы; тесты используют её и не дублируют работу с процессами.

```python
# conftest.py
import json, os, subprocess

BIN = os.environ["GHREPORT_BIN"]
BASE = os.environ["GITHUB_API_BASE_URL"]

def run_ghreport(repos, cache_dir, *args):
    cmd = [BIN, "--repos", repos, "--out", "-",
           "--cache-dir", str(cache_dir), *args]
    env = dict(os.environ, GITHUB_API_BASE_URL=BASE)
    return subprocess.run(cmd, capture_output=True, text=True,
                          env=env, timeout=120)

def report_of(proc):
    assert proc.returncode == 0, proc.stderr
    return json.loads(proc.stdout)

# test_example.py
def test_report_schema(tmp_path):
    proc = run_ghreport("stub/alpha", tmp_path / "cache")
    report = report_of(proc)
    assert report["repos"][0]["repo"] == "stub/alpha"
    assert report["repos"][0]["error"] is None
```
