# План разработки msgfmt (часть 1)

План и приведённые ниже трактовки утверждены пользователем. Активная
спецификация — [task1_cplusplus.md](task1_cplusplus.md); порядок работы —
[AGENTS.md](../AGENTS.md). Изменения исходного ТЗ не требуются.

Разработка и проверки выполняются GCC на Windows. Сохраняем переносимость
на Linux; пользователь проверит Linux после завершения проекта. Коммиты,
push и решения о ветках остаются за пользователем.

## Архитектура

Только C++17 и стандартная библиотека; CMake >= 3.20 и CTest. Без сторонних
парсеров, тестовых библиотек и дополнительных зависимостей тестирования.

```text
msgfmt/
  CMakeLists.txt
  README.md
  include/msgfmt.hpp
  src/utf8.hpp
  src/utf8.cpp
  src/msgfmt.cpp
  src/main.cpp
  tests/test_main.cpp
  tests/cli_tests.cmake
```

- `msgfmt_lib` — библиотечная цель, `msgfmt` — исполняемая цель.
- `msgfmt.hpp` — стили, диапазоны, результат разбора, ошибка `invalid_utf8`,
  функции `parse` и `escape` с входом `std::string_view` и результатом
  `std::variant`. Возвращаемые строки владеют данными; позиции — `std::size_t`.
- `utf8.*` — декодирование, проверка UTF-8, длина кодовой точки в UTF-16,
  классификация символов.
- `msgfmt.cpp` — стековый разбор, экранирование, формирование диапазонов.
- `main.cpp` — байтовый ввод-вывод, CLI и собственная сериализация JSON.
- Тесты на C++; CMake запускает CLI и сравнивает вывод и коды возврата.
  Бинарные фикстуры создаются тестовой программой в каталоге сборки.

Дополнительное разделение файлов — только при практической необходимости.
Публичный потоковый API, расширяемая грамматика и части 2–3 не входят в работу.

## Согласованный контракт

### UTF-8 и классификация

- Строго проверяем весь вход: усечение, неверные байты, overlong encoding,
  суррогаты и значения выше U+10FFFF недопустимы. Проверка действует также
  внутри code, URL и неудачных конструкций. Частичный результат не выдаётся.
- Не нормализуем Unicode; сохраняем обычные байты, BOM, NUL, CR и LF.
- В чистом тексте BMP-кодовая точка занимает одну единицу UTF-16,
  supplementary — две. Combining marks считаются отдельно, графемы не выделяем.
- Буквы: `A–Z`, `a–z`, U+0400–U+0481, U+048A–U+04FF. Цифры: `0–9`.
  Остальные корректные кодовые точки принимаются, но не считаются буквами
  или цифрами для границ `_`. Это согласованное ограничение классификации.
- Пробелы — Unicode 17.0 `White_Space`: U+0009–000D, U+0020, U+0085,
  U+00A0, U+1680, U+2000–200A, U+2028–2029, U+202F, U+205F, U+3000.
  Обширных таблиц и зависимости от системной локали не вводим.
- Соседние символы условий открытия/закрытия — кодовые точки исходного входа.

Источники классификации:
[кириллица](https://www.unicode.org/Public/17.0.0/ucd/UnicodeData.txt),
[White_Space](https://www.unicode.org/Public/17.0.0/ucd/PropList.txt).

### Разметка и восстановление литералов

- Один курсор разбора слева направо и стек открытых конструкций.
  Декодируем UTF-8 по мере чтения. Финальная сборка результата и сортировка
  не являются повторным разбором входа.
- Закрывается только вершина стека. Маркер уже открытого ниже стиля — текст.
  Повторно тот же стиль не открывается; частичные пересечения исключены.
- В code содержимое дословное: разметка и экранирование не действуют.
- Результат конструкции предварителен до её завершения. Неудачная конструкция
  возвращается целиком исходными байтами, включая вложенные маркеры и слеши.
  Её вложенные предварительные диапазоны отбрасываются. Подтверждённые
  фрагменты вне этой конструкции сохраняются. Повторно вход не разбираем.
- Пустые bold/code-конструкции, включая `****` и две соседние обратные
  кавычки, остаются литералами: между маркерами требуется содержимое.
- Сортировка: offset по возрастанию, length по убыванию, затем порядок
  открытия стиля. Порядковый номер открытия — внутренние данные, не поле JSON.

| Вход | Текст | Диапазоны |
| --- | --- | --- |
| `**a _b_ c**` | `a b c` | bold(0, 5), italic(2, 1) |
| `**a _b_` | `**a _b_` | нет |
| `_a **b**` | `_a **b**` | нет |
| `**ok** **bad _x_` | `ok **bad _x_` | bold(0, 2) |
| `**a _b** c_` | `**a _b** c_` | нет |
| `**a _b** c_ d**` | `a b** c d` | bold(0, 9), italic(2, 5) |
| `[**a**]()` | `[**a**]()` | нет |

В контрольном примере № 9 ТЗ проверяем `bold(0, 15); italic(7, 8)`:
маркеры охватывают «и курсив». Значение `italic(7, 1)` и пояснение в ТЗ
противоречат правилам, которым само ТЗ отдаёт приоритет.

### Ссылки и escape

- Подпись и URL непусты. В подписи возможны вложенные стили; в URL разметка
  не интерпретируется. Пробелы в URL запрещены; адреса не валидируем.
- Общее экранирование действует в подписи и URL, кроме содержимого code.
  Пара «обратный слеш + служебный символ» обрабатывается раньше разделителей.
  Полученный обычный символ повторно как разметка не рассматривается.
- Согласованное уточнение п. 8: `]` и `)` запрещены как неэкранированные
  разделители внутри соответствующего содержимого. Экранированные символы
  допустимы в результате и не закрывают конструкцию.
- Перед неслужебным символом слеш сохраняется. Снятие экранирования однократное.
- Перед завершающим подпись `]` требуется непробельный символ:
  `[a ](u)` — литерал. Круглые скобки URL не балансируем.
- Функция `escape` добавляет слеш перед каждым из символов `*`, `_`,
  обратной кавычкой, `[`, `]`, `(`, `)`, обратным слешем.
- Для корректного UTF-8 проверяем: `parse(escape(x))` возвращает текст `x`
  без диапазонов.

В таблице слеши записаны буквально, без C++/JSON-экранирования.

| Вход | Текст | Ссылка |
| --- | --- | --- |
| `[a\]b](u)` | `a]b` | link(0, 3, "u") |
| `[x](a\)b)` | `x` | link(0, 1, "a)b") |
| `[x](a\(b\))` | `x` | link(0, 1, "a(b)") |
| `[a\_b](u)` | `a_b` | link(0, 3, "u") |
| `[x](a\qb)` | `x` | link(0, 1, "a\qb") |
| `[x](a b)` | `[x](a b)` | нет |
| `[x](a(b)c)` | `xc)` | link(0, 1, "a(b") |

### CLI

- Без аргументов — JSON разбора; `escape` — непосредственно экранированный
  текст. Весь stdin читается до вывода результата.
- Успех — код 0. Неверный UTF-8 — код 2 и только
  `{"error":"invalid_utf8"}` в stdout.
- Неизвестные аргументы и ошибки ввода-вывода — код 1, диагностика в stderr,
  без нового JSON-контракта ошибок.
- Автоматический завершающий перевод строки не добавляется.
- JSON: только поля ТЗ, фиксированный порядок, корректное экранирование
  кавычек, слешей и U+0000–001F. Остальные UTF-8-байты сохраняются.
  Числа не зависят от локали.
- На Windows стандартные потоки переводятся в бинарный режим;
  платформенный код локализован в main.cpp.

## Этапы и критерии готовности

Каждый этап — естественная точка для ручного коммита пользователя.

1. **Контракт и каркас сборки.** Сохранить утверждённый план; создать структуру,
   публичный API, цели библиотеки/CLI/тестов и CTest. Объявления parse/escape
   ещё без реализации; не подменять её успешными заглушками. CLI явно сообщает
   о незавершённом этапе и возвращает 1. Готовность: конфигурация и сборка GCC,
   проверки публичных типов/сигнатур и запуска CLI проходят без предупреждений.
2. **UTF-8 и escape.** Декодер, классификация, UTF-16 и экранирование.
   Тесты: границы кодировок, основные классы неверного UTF-8, NUL/BOM/CR/LF,
   supplementary и combining marks, каждый служебный символ и цепочки слешей.
   Готовность: модульные проверки выполнены, доступные санитайзеры чисты.
3. **Парсер.** Стек, стили, ссылки, возврат литералов и сортировка.
   Тесты: все 15 примеров с оговоркой № 9, правила 3.5, согласованные случаи
   вложенности/ссылок, границы слов, пробелы и UTF-16, совпадающие интервалы.
   Готовность: каждое правило покрыто, частичных пересечений нет.
4. **CLI и JSON.** Настоящие режимы, бинарные потоки, сериализация.
   Тесты процесса: stdout/stderr/код, пустой и многострочный ввод, NUL и JSON-
   управляющие символы, неверный UTF-8 в code/URL/после корректного префикса,
   аргументы и ошибки ввода-вывода. Заменить временный тест каркаса CLI.
   Готовность: проверен контракт 3.6, нет частичного вывода при неверном UTF-8.
5. **Итоговая проверка и документация.** Детерминированные генерируемые входы,
   свойство parse(escape(x)), границы/сортировка/повторяемость результата,
   длинные цепочки маркеров. Полный Release и доступные ASan/UBSan.
   Проверка каждого пункта ТЗ. README библиотеки: API, команды, примеры,
   решения и ограничения. Корневой README: текущая часть и использованные
   инструменты. Готовность: проверено Windows GCC, подготовлены Linux-команды,
   непроверенные платформы и санитайзеры явно отмечены.

## Сборка и тесты

- Обязательный C++17 без расширений, `-Wall -Wextra` для GCC/Clang.
- `include(CTest)`, тесты включены по умолчанию. Проверки работают в Release,
  не полагаются только на `assert`. Тестовые данные — в каталоге сборки.
- Опция `MSGFMT_ENABLE_SANITIZERS` включает `-fsanitize=address,undefined`
  при компиляции и линковке, отладочную информацию и frame pointers.
  Проверять поддержку; при недоступности выдавать явную ошибку конфигурации,
  не отключать опцию молча и не считать проверку выполненной.
- Каталоги сборки не включаются в Git. Команды ТЗ для Linux сохраняются:

```text
cmake -S msgfmt -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build
```

На Windows выбрать GCC-совместимый генератор (например, Ninja) явно и записать
проверенную команду в README. Не требовать WSL, MSVC, Python или сети.

После каждого этапа сообщать изменения, выполненные проверки и ограничения.
Windows-проверка не подтверждает Linux; отсутствие sanitizer runtime не
считается успешным запуском санитайзеров.

## Выполнение этапа 2

Реализованы внутреннее декодирование одной кодовой точки UTF-8 по байтовому
смещению, ширина UTF-16, проверка/длина всей строки, фиксированные классы букв,
цифр и White_Space. EOF/недопустимое смещение и неверная последовательность
возвращают отсутствие кодовой точки; декодер не читает за границами string_view.

Реализована публичная escape: один проход с проверкой UTF-8, исходные байты
обычных символов сохраняются, перед каждым служебным символом добавляется
слеш. При неверном UTF-8 возвращается только Error::invalid_utf8.
Публичный интерфейс не расширен; парсер и CLI остаются на этапах 3–4.

Проверено: GCC 14.2.0, Windows, MinGW Makefiles, Release,
`-std=c++17 -Wall -Wextra`, без предупреждений. CTest — 4/4:
публичный API, UTF-8/UTF-16/классификация, escape, каркас CLI.
Проверки включают все 1 112 064 скалярных значения Unicode, все 256
однобайтовых и 65 536 двухбайтовых входов, пограничные и ошибочные
последовательности длиной 2–6 байтов, NUL/BOM/CR/LF, noncharacters,
combining marks, supplementary-символы, 25 White_Space и цепочки слешей.

Свойство parse(escape(x)) будет проверено после реализации parse на этапе 3.
ASan/UBSan на этом этапе не запускались: ранее установлено отсутствие runtime
в доступном GCC; повторная проверка того же ограничения не выполнялась.
Linux не проверен. Агент коммитов не создавал и ветку не менял.
