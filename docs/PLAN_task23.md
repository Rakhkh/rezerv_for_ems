# План разработки ghreport

Дата: 2026-10-24.

Статус: начальная версия согласованного плана. Реализация службы ещё не начата.

## 1. Область работы и источник требований

Единственная активная спецификация — [task23_go_python.md](task23_go_python.md).
Общие правила работы находятся в [AGENTS.md](../AGENTS.md).
Этот план фиксирует порядок реализации и согласованные решения по пробелам ТЗ;
он не заменяет спецификацию.

Текущий этап разработки охватывает только часть 2: консольную службу ghreport
на Go, её Go-тесты, Docker-образ и документацию. Требования части 3 учитываются
при проектировании, но Python-тесты будут отдельно спланированы и написаны
после завершения службы. Реализация msgfmt на C++ находится вне области работы:
её исходники, сборка и тесты не затрагиваются.

Работа ведётся в отдельной ветке `feat/service`. Git-коммиты создаёт пользователь
после проверки изменений. Автоматические коммиты, push и переключение веток
не выполняются. Секреты, кэш, журналы и результаты сборки не включаются в коммиты.

## 2. Основные архитектурные решения

- ghreport — однократно запускаемая консольная программа: прочитать конфигурацию,
  последовательно обработать репозитории, записать результат и завершиться.
  HTTP-сервер, планировщик и фоновые задачи не нужны.
- Исходники размещаются в `service/`, отдельный модуль Go с минимальной версией
  языка 1.22. Не используются API стандартной библиотеки, требующие более нового Go.
- Достаточно одного пакета `main` с разделением ответственности по файлам.
  Дополнительные пакеты вводятся только при возникновении конкретной необходимости.
- Используется только стандартная библиотека Go. GitHub SDK, включая go-github,
  сторонние HTTP-клиенты и библиотеки тестирования не нужны.
- Все HTTP-запросы, включая страницы, перенаправления и повторные попытки,
  выполняются последовательно. Репозитории используются только для чтения.
- Для модульных тестов передаются HTTP-клиент и функции получения времени и
  ожидания. Универсальные интерфейсы хранилищ и инфраструктура внедрения
  зависимостей не вводятся.
- Программа проверяется как отдельный процесс с первого этапа разработки.
  Работающий сквозной сценарий появляется на втором этапе.

Предполагаемая структура; небольшие файлы можно объединять без изменения
ответственности компонентов:

```text
service/
  go.mod
  main.go           вход в программу, выполнение и код завершения
  config.go         аргументы, окружение и валидация
  client.go         HTTP-запрос, перенаправления и получение страницы
  retry.go          классификация временных ошибок и ожидание
  pagination.go     разбор Link
  cache.go          файловый кэш страниц
  collect.go        обход страниц, фильтрация и дедупликация
  report.go         модели отчёта, сортировка и вывод JSON
  trace.go          журнал HTTP-обмена в JSON Lines
  *_test.go
  Dockerfile
  .dockerignore
  README.md
```

Основной поток данных:

```text
CLI и окружение
  -> конфигурация
  -> последовательный сбор репозиториев
     -> получение страницы: HTTP, перенаправления, повторы, кэш, trace
     -> фильтрация и дедупликация
  -> сортировка и формирование результата
  -> вывод JSON и код завершения
```

## 3. Конфигурация и вывод

### 3.1. Аргументы и окружение

Все аргументы проверяются до сетевых запросов, создания кэша и открытия файлов
отчёта и журнала. Значения по умолчанию соответствуют разделу 4.2 ТЗ:
`--limit 100`, `--out -`, `--cache-dir ./ghreport-cache`; дата и trace не заданы.

- `--repos` обязателен. Каждый элемент содержит две непустые части `owner/repo`.
  Внешние пробелы элементов удаляются. Дубликаты определяются по точному
  совпадению получившихся строк, с сохранением первого вхождения и его написания.
  Дополнительные ограничения на имена GitHub сверх необходимой проверки формата
  не вводятся.
- `--limit` — целое число не меньше 1.
- `--since` строго соответствует `YYYY-MM-DD`; граница включения — 00:00:00 UTC.
- Неизвестные параметры и лишние позиционные аргументы являются ошибкой CLI.
- Ошибка аргументов даёт код 2, диагностику в stderr и пустой stdout.
- `GITHUB_API_BASE_URL` читается из окружения процесса. Только отсутствие
  переменной включает значение `https://api.github.com`. Заданный адрес
  валидируется; пустое или некорректное значение не подменяется адресом GitHub.
  Ошибка адреса рассматривается как ошибка конфигурации с кодом 2.
- Поддерживаются схемы HTTP и HTTPS, завершающий слеш и префикс пути базового
  адреса, например `/api/v3/`. HTTP необходим для управляемого локального сервера.
- Непустой `GITHUB_TOKEN` передаётся как `Authorization: Bearer <token>`.
  При отсутствии токена или пустом значении заголовок не отправляется.
- Адрес и токен не фиксируются в исходниках или Docker-образе. Автоматического
  возврата к публичному GitHub при ошибках другого сервера нет.

### 3.2. Формирование результата

- Результат собирается до записи отчёта. Фатальный `401` отменяет выдачу ранее
  собранных результатов.
- Обычный отчёт при `--out -` записывается в stdout; при файловом `--out` —
  в указанный файл, stdout остаётся пустым.
- Фатальные объекты `{"error":"unauthorized"}` и `{"error":"all_failed"}`
  записываются в stdout независимо от `--out`, согласно разделу 4.4.6 ТЗ.
- В stdout нет диагностических сообщений. Диагностика направляется в stderr.
- Вывод — один JSON-объект UTF-8 со всеми обязательными полями раздела 4.5 ТЗ.
  Пустые `issues` и `labels` кодируются как `[]`, успешный `error` — как `null`.
- Порядок репозиториев сохраняется после дедупликации аргумента `--repos`.
- `count` равен длине итогового массива issue; порядок labels соответствует API.
- `generated_at` формируется один раз при подготовке результата в UTC/RFC3339.
- Строка `created_at` сохраняется как в API; для сравнения и фильтрации
  используется разобранное время, включая смещения и дробные секунды.

## 4. Получение и обработка страниц

### 4.1. HTTP и перенаправления

Один переиспользуемый `http.Client` обслуживает все обращения. Таймаут каждого
HTTP-запроса — 30 секунд, включая соединение и чтение тела. Тела ответов
закрываются до следующего обращения или ожидания.

Начальный адрес строится через `net/url`:

```text
GET {base}/repos/{owner}/{repo}/issues
state=open&sort=created&direction=asc&per_page=100
```

Порядок параметров в строке запроса не является частью контракта. Параметр
`since` API не используется, поскольку он относится к дате обновления.

Обязательные заголовки:

- `Accept: application/vnd.github+json`;
- `User-Agent: ghreport/1.0`, с описанием в README;
- `X-GitHub-Api-Version: 2026-03-10`;
- `Authorization: Bearer <token>` при наличии токена.

Перенаправления обрабатываются явно; автоматическое следование в `http.Client`
отключается. Это позволяет журналировать каждый HTTP-запрос и выбирать кэш
по фактическому адресу.

- Для `301` используется `Location`, постоянное соответствие адресов
  запоминается для будущих обращений в метаданных кэша.
- Для `302/307` используется `Location` только в текущем обращении.
- Относительный адрес разрешается относительно URL ответа.
- Переходы ограничиваются десятью перенаправлениями, циклы обнаруживаются.
- Валидатор кэша одного адреса не переносится на другой адрес.
- Токен передаётся только исходному origin: та же схема, хост и порт,
  что у настроенного API. Переход на другой origin не получает токен.
- Адреса из `Location` и `Link` не ограничиваются исходным шаблоном пути:
  GitHub может возвращать другой путь того же эндпоинта списка issue.

### 4.2. Пагинация, фильтры и дедупликация

Для каждой страницы:

1. Проверить статус, прочитать тело и разобрать массив JSON.
2. Исключить элементы, у которых присутствует ключ `pull_request`, включая
   значение `null`.
3. При заданном `--since` исключить элементы раньше установленной границы.
4. Исключить номера, уже включённые для текущего репозитория. Сохраняется первая
   подходящая запись; варианты дубликата не объединяются.
5. Включать элементы до достижения `limit`.
6. Если лимит достигнут — закончить без следующего запроса. Иначе перейти
   по `rel="next"` из `Link`; отсутствие `next` завершает обход.

Разбор `Link` учитывает несколько значений заголовка, произвольный порядок
отношений и относительные ссылки. Адрес следующей страницы не конструируется
и его параметры не переписываются. Короткая или пустая страница с `next`
не завершает обход. Повтор URL страницы считается ошибкой ответа, чтобы
предотвратить бесконечный цикл.

Неизвестные поля API игнорируются. Синтаксис JSON, структура массива и поля,
необходимые для отчёта и сравнения времени, проверяются; непригодные данные
не заменяются молча нулевыми значениями.

После выбора issue сортируются по моменту `created_at`, затем по `number`,
оба ключа по возрастанию. Выбираются первые N подходящих уникальных элементов
в порядке обхода API; дополнительные страницы после лимита ради разрешения
равных дат не загружаются. Это сохраняет алгоритм остановки из раздела 4.4.2 ТЗ.

## 5. Ошибки и повторные попытки

### 5.1. Повторы

Сетевые ошибки, ошибки чтения тела и ответы `5xx`: первоначальная попытка
и максимум три повтора с ожиданием 1, 2 и 4 секунды. После исчерпания —
`request_failed` у репозитория.

Rate limit определяется только для `403/429` при наличии хотя бы одного
признака из ТЗ: сообщение об ограничении в теле, заголовок `Retry-After`
или `X-RateLimit-Remaining: 0`. Обычный `403` не считается rate limit.

Лимит повторов при rate limit — два повтора на запрашиваемый адрес.
Порядок расчёта паузы:

1. Корректный `Retry-After`: число секунд или HTTP-дата.
2. Иначе — до времени `X-RateLimit-Reset` в UTC epoch.
3. Иначе — 60 секунд перед первым повтором и 120 перед вторым.

Истёкшее корректное время означает отсутствие оставшегося ожидания. Некорректное
значение заголовка не используется, применяется следующий источник паузы.
Заданная сервером пауза не сокращается ради скорости тестов. После исчерпания
повторов результат репозитория — `rate_limited`.

Счётчики сетевых повторов и повторов rate limit не сбрасываются при чередовании
ошибок одного запрашиваемого адреса: последовательность остаётся конечной.
Ожидание реализуется через заменяемую в Go-тестах функцию. Пользовательских
флагов или переменных окружения для ускорения тестов не добавляется.

### 5.2. Согласованные трактовки ошибок

Следующие решения закрывают неоднозначности, выявленные при обсуждении ТЗ:

| Ситуация | Поведение |
| --- | --- |
| Ответ `401` на любой странице | Немедленное завершение всего запуска, код 3, `unauthorized` в stdout; тело ошибки не требуется разбирать как страницу. |
| Ответ `404` | `not_found` у текущего репозитория, без повторов. |
| Некорректный JSON | `invalid_response`, без повторов. |
| JSON непригодной структуры, неверная дата или отсутствующее необходимое поле | `invalid_response`, без выдумывания значений. |
| Ошибочный Link, цикл страниц, необоснованный `304` | `invalid_response`. |
| Обычный `403`, `422` и другой неожиданный HTTP-статус | `request_failed`; повторы только для категорий из раздела 5.1 этого плана. |
| Некорректное перенаправление или превышение его лимита | `request_failed`, без бесконечных переходов. |
| Ошибка на последующей странице репозитория | Частичная выборка отбрасывается: заполнен `error`, `count: 0`, `issues: []`. |
| Успешный репозиторий без подходящих issue | Успех: `error: null`, `count: 0`, `issues: []`. |
| Все репозитории успешны | Отчёт и код 0. |
| Есть успешные и ошибочные репозитории | Отчёт и код 1. |
| Все репозитории завершились с ошибками | Код 3, `all_failed` в stdout. |
| Невозможно создать кэш, открыть trace или записать отчёт; иная невосстановимая локальная ошибка ввода-вывода | Код 3, безопасная диагностика в stderr; новый JSON-код ошибки не вводится, успешный отчёт не выдаётся. |

Последняя строка — согласованное уточнение пробела ТЗ: раздел 4.4.6 не задаёт
вывод для локальных ошибок. Если ошибка обнаружена непосредственно при записи
в stdout, уже записанные байты вернуть невозможно; завершение остаётся ошибочным.

Ошибка отдельного репозитория не мешает обработке остальных, кроме глобального
`401` и невосстановимых локальных ошибок.

## 6. Постоянный кэш

Кэш хранит исходные страницы API, а не отфильтрованные отчёты. Один каталог
пригоден для разных `--limit` и `--since`.

На полный URL приходится JSON-запись с именем на основе SHA-256 адреса.
Сохраняются версия формата, URL, ETag, тело и значения `Link`. Для постоянного
перенаправления сохраняется соответствие исходного и целевого URL. Точные поля
формата описываются в README. Токен и заголовки запросов не сохраняются.
Разные базовые адреса разделены ключами полного URL.

- При пригодной записи с ETag отправляется `If-None-Match`. Кавычки и `W/`
  в валидаторе сохраняются.
- При `200` используется новое тело и после успешного разбора обновляется кэш;
  `from_cache: false`.
- При `200` без ETag новая запись не использует старый валидатор. Следующий
  запрос будет безусловным.
- При `304` используется сохранённое тело; `from_cache: true`.
- Присутствующие в `304` метаданные обновляют запись. Если `Link` в `304`
  отсутствует, используется сохранённый `Link`. Это необходимо для повторного
  обхода многостраничной выдачи.
- При `304` без отправленного валидатора или без пригодного сохранённого тела
  фиксируется `invalid_response`.
- Повреждённая запись считается промахом кэша с диагностикой; выполняется
  безусловный запрос. Прочие ошибки доступа к файловой системе не скрываются.
- Сетевая ошибка или `5xx` не разрешает выдавать старое тело как успешный ответ:
  автономного режима работы с устаревшими данными в ТЗ нет.

Тело, ETag и Link записываются вместе через временный файл в том же каталоге
и замену основной записи. Детали замены проверяются на Windows и Linux:
нельзя предполагать одинаковые гарантии атомарности на всех платформах.
Полноценная поддержка нескольких процессов с общим кэшем не входит в объём ТЗ.

## 7. HTTP trace и секреты

- При `--trace` файл открывается заново для текущего запуска. Без параметра
  журнал не создаётся.
- Каждое выполненное HTTP-обращение даёт одну JSON-строку, включая переходы
  и повторные попытки, в порядке выполнения.
- Обязательные поля: `ts`, `method`, `url`, `status`, `attempt`, `from_cache`,
  `error`. Время — UTC/RFC3339, URL — полный фактический адрес.
- `attempt` начинается с 1 для очередного запрашиваемого адреса и увеличивается
  при его повторах. Адрес перенаправления начинает свою последовательность с 1.
- `status` — фактический код ответа; 0 только при отсутствии HTTP-ответа.
  Ошибка чтения тела после получения заголовков не обнуляет полученный статус.
- Для `304` статус остаётся 304; `from_cache: true` только при успешном
  использовании сохранённого тела.
- При успехе `error: null`; при ошибке — краткое безопасное обозначение,
  например `timeout`, `network`, `invalid_response` или `http_404`.
- Заголовок Authorization, токен, полная конфигурация, сырые тела ошибок
  и необработанные транспортные ошибки в диагностику и trace не записываются.
- Ошибки записи и закрытия файлов проверяются; отказ журнала не скрывается.

## 8. Этапы реализации и контрольные точки

Каждый этап заканчивается работающим в своей заявленной области результатом,
релевантными тестами и кратким отчётом пользователю. Неполная реализация
промежуточного этапа не объявляется полностью соответствующей ТЗ.
После проверки пользователь может создать отдельный коммит.

### Этап 1. Модуль, CLI и модели

Результат: `service/go.mod`, вход в программу, разбор конфигурации, модели
отчёта и ошибок, функция выполнения с возвращаемым кодом завершения.

Проверки:

- Табличные Go-тесты значений по умолчанию, списка репозиториев, даты,
  лимита, окружения и некорректных аргументов.
- Сборка и запуск реального бинарника отдельным процессом: код 2,
  пустой stdout, диагностика в stderr; отсутствие файловых и сетевых действий
  при ошибках аргументов.
- `go test ./...`, `gofmt -l .`, `go vet ./...`.

Критерий готовности: проверен реальный вход в программу и контракт ошибок CLI.
Контрольная точка коммита: основа Go-службы и тесты конфигурации.

### Этап 2. Минимальный сквозной сценарий

Результат: CLI -> HTTP GET одной страницы -> разбор issue -> JSON-отчёт.
Сразу используются обязательные параметры, заголовки, заданный API base URL
и таймаут. Отчёт соответствует полной схеме ТЗ, а не временно упрощённой схеме.

Проверки:

- `httptest.Server` проверяет метод, путь, параметры, заголовки, наличие
  и отсутствие токена, префикс пути и завершающий слеш базового адреса.
- Подготовленный одностраничный ответ без PR и с числом issue ниже лимита
  проверяет отображение полей, Unicode, labels и пустой результат.
- Реальный бинарник запускается отдельным процессом с локальным сервером:
  успешный код, правильная схема отчёта и чистый stdout.
- Тот же сценарий доступен для ручного запуска.

Критерий готовности: есть запускаемый сквозной сценарий; полная пагинация,
фильтры, кэш и отказоустойчивость пока не заявляются реализованными.
Контрольная точка коммита: одностраничный сбор и отчёт.

### Этап 3. Полный сбор и результаты репозиториев

Результат: пагинация, лимит, фильтрация PR и since, дедупликация, сортировка,
несколько репозиториев и основные коды завершения.

Проверки:

- Несколько страниц, разные формы Link, пустая промежуточная страница с next,
  остановка без лишнего запроса после лимита и цикл ссылок.
- PR с `pull_request: null`, граница даты включительно, повторы номеров,
  сохранение первой записи, одинаковые даты и корректное сравнение времени.
- Некорректный JSON и непригодная структура; неизвестные поля не мешают разбору.
- Успешный пустой репозиторий, частичный отказ, все ошибки, немедленный `401`,
  отбрасывание неполной выборки после ошибки следующей страницы.
- Проверки реального процесса: полноценный отчёт, порядок репозиториев,
  коды 0/1/3 и фатальные объекты из приложения Б.

Критерий готовности: правильный отчёт для многостраничной выдачи и определённое
поведение ошибок репозиториев. Контрольная точка коммита: сбор issue и ошибки.

### Этап 4. Отказоустойчивость и полный trace

Результат: перенаправления, сетевые повторы, rate limit и журнал каждой попытки.

Проверки:

- `301/302/307`, относительный Location, цикл и предел переходов,
  непередача токена другому origin, журналирование каждого обращения.
- Подменённое ожидание подтверждает интервалы 1/2/4 и число повторов.
- `403/429` по каждому признаку rate limit, обычный `403`, приоритет заголовков,
  HTTP-дата, некорректные значения, резервные паузы и конечность смешанных ошибок.
- Таймаут и ошибка чтения тела; корректный статус в trace.
- Проверки процесса против управляемого сервера: восстановление после сбоя,
  последовательность запросов, номера попыток и JSON Lines.
- Во всех сценариях одновременно активен максимум один HTTP-запрос.

Критерий готовности: соблюдены конечные политики повторов и наблюдаемость
каждого обращения. Контрольная точка коммита: HTTP-отказоустойчивость и trace.

### Этап 5. Постоянный ETag-кэш

Результат: файловый кэш, If-None-Match, обработка 304, сохранённая пагинация
и метаданные постоянных перенаправлений.

Проверки:

- Два отдельных запуска бинарника с одним каталогом кэша: первый 200,
  второй 304; отчёты равны, кроме generated_at.
- Многостраничный второй запуск с 304 без Link; разные limit и since
  при повторном использовании исходных страниц.
- Обновление тела и ETag по 200, слабый ETag, ответ без ETag,
  обновление метаданных по 304, необоснованный 304.
- Повреждённая запись, ошибки файловой системы, разделение API base URL,
  повторное использование постоянного перенаправления.
- Отсутствие токена в созданных файлах, stdout, stderr и trace.
- Замена файлов кэша и закрытие файлов на Windows; Linux-проверка также
  выполняется при появлении контейнерного окружения.

Критерий готовности: кэш работает между процессами, не теряет следующие страницы
и не подменяет ошибки устаревшими данными. Контрольная точка коммита: ETag-кэш.

### Этап 6. Комплексная проверка программы

Результат: окончательно проверены сочетания уже реализованных возможностей,
файловый вывод и локальные ошибки. Это не первый запуск программы как процесса.

Проверки:

- `--out -` и файловый --out; trace включён и выключен.
- Фатальные объекты при файловом --out, чистые потоки вывода,
  ошибки открытия, записи и закрытия файлов.
- Несколько репозиториев, страницы, кэш и повторы в одном сценарии;
  отсутствие утечек секрета на ошибочных путях.
- Сопоставление схемы и поведения с разделами 4.2–4.7 и примерами Б.1–Б.4 ТЗ.
- Сборка, полный Go-набор, gofmt и go vet.

Критерий готовности: контракт консольной программы проверен целиком.
Контрольная точка коммита: комплексные проверки и необходимые исправления.

### Этап 7. Docker, документация и Linux-проверка

Результат: Dockerfile, .dockerignore, README службы, окончательная проверка
на Linux и сверка с ТЗ.

Проверки:

- `docker build -t ghreport service/` из корня репозитория.
- Go-тесты, gofmt и go vet в Linux-окружении с проверкой заявленного минимума
  Go 1.22; версии сборочного инструментария фиксируются явно.
- Запуск финального образа от непривилегированного пользователя, доступность
  рабочего каталога для кэша, trace и файлового отчёта.
- Передача токена и произвольного API base URL при запуске, отсутствие
  секретов в образе, доступность CA-сертификатов для HTTPS.
- Сценарии процесса из контейнера против управляемого API, включая кэш.
- Публичный API может использоваться для дополнительной ручной проверки,
  но не является зависимостью обязательных детерминированных тестов.

Критерий готовности: Go-служба, контейнер и документация соответствуют части 2;
зафиксированы результаты проверок и оставшиеся ограничения, если они есть.
Контрольная точка коммита: контейнеризация и документация.

## 9. Общие правила проверки и окружение

Разработка и отладка выполняются на Windows. Пишется переносимый Go-код:
`filepath` для путей, закрытие файлов, запуск процессов без зависимости
от PowerShell/Bash, учёт расширения `.exe`.

Основные команды из `service/`:

```text
go test ./...
gofmt -l .
go vet ./...
go build .
```

Критерии: тесты проходят, gofmt ничего не выводит, go vet не даёт замечаний,
сборка успешна. После изменений выполняются релевантные проверки; перед сдачей —
полный набор на Windows и Linux. Проверка сборки более новым Go сама по себе
не подтверждает совместимость с Go 1.22.

Go-тесты используют `testing`, `httptest`, временные каталоги и управляемые
ответы. Сборка бинарника для проверок процесса выполняется в тестовый временный
каталог и переиспользуется в пределах подходящей группы тестов. Подробные
комбинаторные проверки логики остаются модульными; матрица целиком не дублируется
через запуск процесса. Ожидание процессов ограничено по времени.

Длительные задержки в модульных тестах заменяются управляемым ожиданием.
Небольшой реальный Retry-After проверяется на уровне процесса. Случайные sleep
для синхронизации тестов не используются.

При первоначальной проверке среды доступны Go 1.27.2, Docker CLI 28.4.0
и Python 3.14.2. Docker daemon и режим Linux containers ещё не проверены.
Go сообщил об ограничении записи телеметрии вне workspace; при необходимости
для команд разработки используется `GOTELEMETRY=off`. Это настройка инструментов,
а не переменная конфигурации ghreport.

## 10. Контейнеризация и документация

Двухэтапная сборка: зафиксированный совместимый образ Go для builder,
`CGO_ENABLED=0` для Linux-бинарника, финальный `scratch` с бинарником,
CA-сертификатами и подготовленным рабочим каталогом.

- Непривилегированный числовой `USER` задаётся явно.
- Рабочий каталог принадлежит этому пользователю и доступен для записи.
- `ENTRYPOINT` запускает ghreport; параметры передаются без shell-обёртки.
- Финальный образ не требует файлов с хоста для обычного запуска.
- Токен и API base URL не передаются сборке и не фиксируются в образе.
- .dockerignore исключает кэш, журналы, отчёты, бинарники и локальные секреты.
- Проверка наличия Dockerfile не заменяет фактическую сборку, Linux-тесты
  и запуск финального контейнера.

При обращении из контейнера к локальному серверу Windows нельзя использовать
localhost как адрес хоста. Для Docker Desktop используется доступный адрес хоста
(обычно `host.docker.internal`) либо отдельная Docker-сеть. Он передаётся через
GITHUB_API_BASE_URL; программа его не подменяет.

README службы включает запуск, архитектуру, переменные окружения, User-Agent,
формат кэша, лимиты повторов и паузы, примеры вывода, проверки и Docker.
Корневой README обновляется только в относящейся к текущей работе части:
общее описание, запуск, затраченное время и применявшиеся ИИ-инструменты.

## 11. Переход к Python-тестам

После завершения Go-службы составляется отдельный подробный план `api_tests/`.
Ожидаемое окружение: Python не ниже 3.10, pytest не ниже 7. Для набора достаточно
pytest и стандартной библиотеки Python.

Основой будут общий запускатель процесса через абсолютный GHREPORT_BIN,
собственный временный кэш каждого теста, управляемый локальный HTTP-сервер
и отдельные проверки произвольного совместимого API. Проверяются отчёт,
trace, запросы к серверу и коды завершения. Специальный тестовый режим службы,
дополнительные эндпоинты и привязка к фиксированным данным GitHub не нужны.

При проектировании уже учитываются ограничения проверяемости:

- Ровно limit элементов можно требовать только при достаточной подготовленной
  выдаче; универсальное свойство неизвестного API — count <= limit.
- На меняющемся API нельзя гарантировать 304 и идентичность отчётов между
  запусками. Строгий сценарий кэша обеспечивает управляемый сервер.
- PR без ключа pull_request, скрытый пропущенный элемент и отсутствующий Link
  при неизвестной следующей странице нельзя надёжно установить по одной выдаче.
  Для таких проверок нужны эталонные данные управляемого сценария.
- HTTP-сценарии воспроизводятся детерминированно, ожидание процессов ограничено,
  нет зависимости от порядка тестов или сети за пределами настроенного API.
- Полный Python-прогон должен укладываться в 10 минут. Для rate limit сервер
  задаёт небольшую паузу; служба не сокращает настоящие ожидания ради тестов.

Подробный состав Python-тестов и обработка изменчивости внешнего API будут
согласованы отдельно. На текущем этапе каталог api_tests не создаётся.
