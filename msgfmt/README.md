# msgfmt

Библиотека C++17 для преобразования разметки сообщений в UTF-8-текст и
стилевые диапазоны с позициями UTF-16. Спецификация:
[task1_cplusplus.md](../docs/task1_cplusplus.md). Утверждённые решения и этапы:
[PLAN_task1.md](../docs/PLAN_task1.md).

## Текущее состояние: этап 5

Реализованы библиотечные функции `parse` и `escape`, строгий декодер UTF-8,
подсчёт длины UTF-16 и согласованная классификация символов. Подготовлены
CMake-цели, публичные типы и тестовый механизм CTest.

Реализованы оба режима CLI, бинарный ввод-вывод, JSON и обработка ошибок
аргументов и потоков. Тесты разделены по назначению; добавлены проверки
длинных последовательностей и выполнена итоговая сверка с согласованным
контрактом. Сборка и тесты проверены GCC на Windows. Проверки Linux и
ASan/UBSan остаются невыполненными; подробности приведены ниже.

## Командная строка

`msgfmt` читает весь stdin до EOF и выводит один JSON-объект с полями `text`
и `ranges`. `msgfmt escape` выводит непосредственно экранированные байты.
Ввод — UTF-8; перевод строки в конце вывода не добавляется.

| Код | Результат |
| --- | --- |
| 0 | Успешный разбор или escape; stderr пуст |
| 2 | Неверный UTF-8: только `{"error":"invalid_utf8"}` в stdout; stderr пуст |
| 1 | Неверные аргументы или ошибка ввода-вывода; диагностика в stderr |

JSON содержит только поля ТЗ в фиксированном порядке. Кавычки, обратный слеш
и U+0000–U+001F экранируются; остальные UTF-8-байты сохраняются.
Позиции и длины выводятся десятичными целыми независимо от локали.
При неверном UTF-8 частичный успешный результат не выводится, даже если
ошибка обнаружена после большого корректного префикса.

На Windows стандартные потоки работают в бинарном режиме: NUL, Ctrl-Z
и CR/LF не изменяются. При записи проверяется также результат flush.

### Ручная проверка на Windows

После сборки из корня репозитория можно создать UTF-8-файл без BOM и лишнего
перевода строки. Перенаправление через cmd передаёт файлы как байты, без
перекодирования строк конвейером PowerShell:

```powershell
[IO.File]::WriteAllBytes("$PWD\build-gcc\input.txt", [Text.Encoding]::UTF8.GetBytes('🚀 **ок**'))
cmd /d /c ".\build-gcc\msgfmt.exe < .\build-gcc\input.txt > .\build-gcc\result.json"
[IO.File]::ReadAllText("$PWD\build-gcc\result.json", [Text.Encoding]::UTF8)
```

Ожидаемый JSON:

```json
{"text":"🚀 ок","ranges":[{"style":"bold","offset":3,"length":2,"url":""}]}
```

Режим escape:

```powershell
[IO.File]::WriteAllBytes("$PWD\build-gcc\escape-input.txt", [Text.Encoding]::UTF8.GetBytes('2 * 3'))
cmd /d /c ".\build-gcc\msgfmt.exe escape < .\build-gcc\escape-input.txt"
```

Результат — `2 \* 3`. Код возврата можно посмотреть через `$LASTEXITCODE`
сразу после команды cmd. Файлы примера находятся в игнорируемом каталоге сборки.

### Запуск на Linux после сборки

```sh
printf '%s' '**hello**' | ./build/msgfmt
printf '%s' '2 * 3' | ./build/msgfmt escape
```

Ожидаемые результаты: JSON с текстом `hello` и bold(0, 5), затем `2 \* 3`.
Эти команды подготовлены для Linux, но здесь проверены только Windows-команды.

## Библиотечная функция parse

Публичный заголовок — `msgfmt.hpp`, цель для линковки — `msgfmt_lib`.
`msgfmt::parse(std::string_view)` возвращает `ParseResult`:

- `ParsedMessage`: исходный UTF-8 без маркеров и список `Range` с полями
  `style`, `offset`, `length`, `url`;
- `msgfmt::Error::invalid_utf8`, если любая часть входа содержит неверный UTF-8.

Позиции и длины измеряются в кодовых единицах UTF-16 чистого текста,
строки результата владеют данными. Например, `🚀 **ок**` даёт `🚀 ок`
и `bold(3, 2)`. Ошибка не возвращает частичный результат.

Разбор идёт слева направо одним курсором. Стек хранит контрольные позиции
начала конструкции в источнике и результате. Незавершённая или недопустимая
конструкция восстанавливается исходными байтами, а её предварительные
диапазоны удаляются; повторного разбора источника нет. Одновременно открыты
не более четырёх разных стилей. Маркер может закрыть только вершину стека.

Разметка и экранирование внутри code не действуют. В подписи ссылки
разрешены вложенные стили; URL имеет отдельный режим без разбора разметки,
но с общим экранированием. Экранированные `]` и `)` не закрывают ссылку.
Скобки URL не балансируются. Пробелы в URL и пустые подпись/URL недопустимы.

Граница кандидата ссылки определяется разделителями: после `]` без `(`
его префикс возвращается в литералы; при наличии `](` читается URL до первого
неэкранированного `)`. Если кандидат недопустим, он возвращается в литералы,
а следующий фрагмент разбирается обычным образом. Незавершённый кандидат
сохраняется до EOF вместе с вложенным содержимым. Разделители внутри code
считаются обычным содержимым.

Диапазоны сортируются по offset, затем по убыванию length и порядку открытия.
Например, `[**a**](u)` даёт сначала `link(0, 1, "u")`, затем `bold(0, 1)`.
Разбор занимает O(n) до сортировки; сортировка — O(r log r), где r — число
диапазонов. Дополнительная память — O(n + r).

В примере № 9 ТЗ используется согласованная поправка: для
`**жирный _и курсив_**` курсив охватывает «и курсив», то есть `italic(7, 8)`.
Все согласованные трактовки перечислены в плане.

## Библиотечная функция escape

Публичный заголовок — `msgfmt.hpp`, цель для линковки — `msgfmt_lib`.
`msgfmt::escape(std::string_view)` возвращает `EscapeResult`:

- `std::string` с обратным слешем перед каждым символом из набора
  `` * _ ` [ ] ( ) \ ``;
- `msgfmt::Error::invalid_utf8`, если вход содержит некорректный UTF-8.

Например, вход `2 * 3` даёт `2 \* 3`. Уже существующий обратный слеш также
экранируется: операция не является идемпотентной.

Результат владеет своими байтами. Остальной UTF-8 сохраняется без нормализации,
включая BOM, NUL, CR/LF, combining marks и supplementary-символы. Перевод строки
не добавляется. При ошибке частичная строка не возвращается.
Проверка UTF-8 и формирование результата выполняются за один проход,
время и дополнительная память — O(n).

## Unicode-основа

Внутренний модуль `src/utf8.*` читает одну кодовую точку по байтовой позиции
и считает длину строки в кодовых единицах UTF-16. Неверный UTF-8 отвергается,
без подстановки символов замены. Surrogate code points недопустимы, но
корректно закодированные noncharacters, например U+FFFF, принимаются.

Парсер использует фиксированную классификацию:

- буквы: `A–Z`, `a–z`, U+0400–U+0481 и U+048A–U+04FF;
- цифры: `0–9`;
- пробелы: все 25 символов Unicode 17.0 `White_Space`.

Классификация не зависит от системной локали. Остальные символы принимаются
как корректный UTF-8, но не считаются буквами/цифрами для условий разметки.
Например, `é` не входит в выбранный набор букв. Полные диапазоны и источники
зафиксированы в плане. Это ограничение классификации не ограничивает
сохранение текста или подсчёт его длины UTF-16.

## Сборка GCC на Windows

Требуются CMake >= 3.20, GCC с C++17 и `mingw32-make` в PATH.
Из корня репозитория:

```text
cmake -S msgfmt -B build-gcc -G "MinGW Makefiles" -DCMAKE_CXX_COMPILER=g++ -DCMAKE_BUILD_TYPE=Release
cmake --build build-gcc
ctest --test-dir build-gcc --output-on-failure
```

Цели: статическая библиотека `msgfmt_lib`, программа `msgfmt`, тестовая
программа `msgfmt_tests`. Дополнительные зависимости не загружаются.
Для сборки без тестов добавьте `-DBUILD_TESTING=OFF` при конфигурации.

CTest запускает пять групп: `msgfmt.utf8`, `msgfmt.escape`,
`msgfmt.parser`, `msgfmt.cli_streams`, `msgfmt.cli`.
Тестовая программа без аргументов запускает проверки библиотеки и потокового
ядра CLI; можно выбрать группу аргументом `utf8`, `escape`,
`parser` или `cli_streams`. Настоящие процессы CLI запускаются через CTest.

`tests/test_main.cpp` содержит запуск групп и проверки сигнатур при компиляции.
Сценарии находятся в `utf8_tests.cpp`, `escape_tests.cpp`, `parser_tests.cpp`
и `cli_tests.cpp`. Общие данные и сравнение результатов — в `test_support.*`.
Проверки ручного заполнения стандартных контейнеров удалены; владение данными,
NUL и ошибки проверяются на результатах настоящих вызовов `parse` и `escape`.

Тесты проверяют декодирование всех 1 112 064
допустимых скалярных значений Unicode, все одно- и двухбайтовые входы,
граничные и ошибочные последовательности UTF-8, UTF-16, классификацию,
точные результаты escape и контракт CLI. Они работают в Release.
Полный набор из 31 ошибочной последовательности проверяется на уровне декодера.
На границах API и CLI используются шесть представителей: отдельный continuation
byte, overlong, суррогат, значение выше U+10FFFF, неверный continuation byte
и усечение. Для парсера сохраняются разные контексты ошибки, включая code,
подпись, URL, незавершённую конструкцию и подтверждённый префикс.
Группа парсера проверяет все 15 контрольных примеров с поправкой № 9,
вложенность и пересекающиеся маркеры, возврат исходных литералов, ссылки,
экранирование, все 25 White_Space, UTF-16 и сортировку совпадающих интервалов.
Проверяются инварианты диапазонов (границы, целостность суррогатных пар,
отсутствие частичных пересечений) и свойство `parse(escape(x))` на наборе
строк, включая все ASCII-байты, NUL, Unicode и длинные цепочки символов.
Два дополнительных сценария по 10 000 повторений проверяют все диапазоны
последовательных `**a** ` и буквальный откат незакрытого внешнего bold с
вложенными `_🚀_ `. При откате внутренние диапазоны исчезают, а предшествующий
завершённый bold сохраняется. Жёстких порогов времени в этих проверках нет.

`msgfmt.cli` создаёт бинарные фикстуры в `build-gcc/cli-tests/Release`
и выполняет 51 запуск CLI. Сравниваются код возврата и точные байты stdout
и stderr. Проверяются все контрольные примеры, JSON для всех управляющих
символов U+0000–U+001F, кавычки и слеши в URL, NUL/BOM/CR/LF/Ctrl-Z,
пустой и большой ввод, ошибочный UTF-8 и аргументы. Эталонный JSON задан
явно в тестах и не формируется сериализатором приложения.

`msgfmt.cli_streams` подставляет потоки со сбоями чтения, записи и flush
в приватную функцию из main.cpp, а также проверяет независимость чисел JSON
от локали. Для этого main.cpp компилируется в тестовую цель без process main;
публичный интерфейс библиотеки не расширяется. Ошибки потоков проверяются
детерминированно без платформенных скриптов и сторонних зависимостей.
Для GCC/Clang включены `-Wall -Wextra`; расширения C++ отключены.

Проверено на Windows: CMake 4.1.2, GCC 14.2.0 (w64devkit), генератор
`MinGW Makefiles`, Release; 5 из 5 тестов прошли, предупреждений компилятора
нет. Ninja в этом окружении зависал на проверке ABI компилятора, поэтому
для воспроизводимой локальной сборки выбран `MinGW Makefiles`.
Сборка с `BUILD_TESTING=OFF` также прошла.

## Санитайзеры

```text
cmake -S msgfmt -B build-gcc-sanitize -G "MinGW Makefiles" -DCMAKE_CXX_COMPILER=g++ -DCMAKE_BUILD_TYPE=Debug -DMSGFMT_ENABLE_SANITIZERS=ON
cmake --build build-gcc-sanitize
ctest --test-dir build-gcc-sanitize --output-on-failure
```

Опция добавляет ASan/UBSan при компиляции и линковке. CMake проверяет наличие
поддержки и runtime-библиотек; если проверка не проходит, конфигурация
завершается ошибкой. Такой результат не считается запуском санитайзеров.

В установленном GCC 14.2.0 проверка линковки обнаружила отсутствие `libasan`
и `libubsan` (`cannot find -lasan`, `cannot find -lubsan`). Конфигурация
с опцией ON отклонена ожидаемым образом; ASan/UBSan здесь не запускались.
