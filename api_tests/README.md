# Интеграционные тесты ghreport

Набор запускает собранную службу отдельным процессом и проверяет её внешний
контракт из [ТЗ](../docs/task23_go_python.md). Порядок разработки и распределение
проверок — в [PLAN_task3.md](../docs/PLAN_task3.md).

Реализованы 75 управляемых случаев CLI, HTTP-запроса,
отчёта, сбора, ошибок API, кэша, повторов, перенаправлений и файловых регрессий.
Проверяются ошибки аргументов без побочных действий, обязательные параметры
и заголовки, отсутствие/пустое значение/наличие токена, префикс и завершающий
слеш base URL, точные поля отчёта, Unicode, labels, исходная дата, generated_at,
вывод в stdout и файл. Добавлены пагинация с пустой промежуточной страницей,
limit, PR/since, дедупликация, UTC-границы и сортировка с точностью до наносекунд,
порядок репозиториев, частичные и фатальные ошибки, trace этих обращений.
Каждый случай имеет отдельные сервер, рабочий каталог
и кэш; настоящий токен и публичный GitHub для этого не нужны.

Кэш проверяется между отдельными процессами, включая 304 без Link, обновление
метаданных, повреждения и отказ от устаревшего результата. Проверены настоящие
паузы повторов, 301/302/307 и trace каждого обращения, отмена отчёта с токеном,
конфликты путей и локальные отказы файловой системы.
В `live/` добавлены два независимых случая для API с неизвестными данными:
свойства отчёта и те же свойства с `--since`. Ещё 10 случаев проверяют регрессии
общих валидаторов trace и времени. Всего в наборе 87 случаев.

## Окружение и запуск

Python не ниже 3.10, pytest не ниже 7. Единственная прямая зависимость — pytest.
Go не ниже 1.22 нужен для предварительной сборки, Docker — только для отдельной
проверки в Linux. Pytest самостоятельно службу не собирает и образы не запускает.

Из корня репозитория, PowerShell:

```powershell
python -m venv "$env:TEMP\ghreport-api-venv"
& "$env:TEMP\ghreport-api-venv\Scripts\python.exe" -m pip install -r api_tests/requirements.txt
go -C service build -o "$env:TEMP\ghreport.exe" .
$env:GHREPORT_BIN = Join-Path $env:TEMP 'ghreport.exe'
& "$env:TEMP\ghreport-api-venv\Scripts\python.exe" -m pytest api_tests -q
```

С уже выбранным Python-окружением команды короче:

```text
python -m pip install -r api_tests/requirements.txt
python -m pytest api_tests/mock -q
pytest api_tests -q
```

`GHREPORT_BIN` должен быть установлен и во втором примере. Это абсолютный путь
к исполняемому файлу, включая `.exe` на Windows; строка команды, `go run`
и `docker run` вместо пути не поддерживаются. Shell-обёртки не используются.

| Настройка | Поведение mock-набора |
| --- | --- |
| `GHREPORT_BIN` | Обязателен, указывает на заранее собранный бинарник. Отсутствующий, относительный или непригодный путь даёт явную ошибку подготовки/запуска. |
| `GITHUB_API_BASE_URL` | Для каждого mock-запуска заменяется URL собственного сервера. Установка этой переменной не переключает mock-набор на другой API. |
| `GITHUB_TOKEN` | Не наследуется mock-процессом: каждый сценарий явно передаёт синтетический токен, пустое значение или отсутствие переменной. |
| `--api-repos` | Список доступных репозиториев для live-группы; на mock-проверки не влияет. |

## Предоставленный API

Из корня репозитория с выбранным Python и установленным `GHREPORT_BIN`:

```powershell
$env:GITHUB_API_BASE_URL = 'https://your-api.example/api/v3/'
python -m pytest api_tests/live -q --api-repos 'owner/repo,owner/other'
pytest api_tests -q --api-repos 'owner/repo,owner/other'
```

В Linux используется `export GITHUB_API_BASE_URL=...`; команды pytest те же.
`GITHUB_TOKEN` необязателен, передаётся из окружения без записи в файлы тестов.
Нужны доступные репозитории; пустой список issue допустим. Имена в `--api-repos`
обрезаются по краям и дедуплицируются с сохранением порядка. URL должен быть
HTTP(S), без credentials, query и fragment; префикс пути и завершающий слеш допустимы.

Если одновременно отсутствуют URL и `--api-repos`, оба live-случая явно
пропускаются. Частичная, пустая или некорректная настройка вызывает ошибку
подготовки. Ошибки доступа, API, сети и службы приводят к провалу теста.
Автоматического обращения к публичному GitHub нет. Прогон с пропущенной
live-группой не считается полной приёмкой.

Каждый live-случай запускает службу один раз с limit=3 и собственным новым кэшем;
второй задаёт since=2020-01-01. Проверяются схема, типы, порядок репозиториев,
граница count, отсутствие дублей, сортировка по моменту создания/номеру,
UTC-граница since, generated_at, поля trace и отсутствие токена в сыром выводе
и декодированных JSON-строках. Данные, количество страниц и наличие PR неизвестны;
не требуются непустая выдача, обязательный 304 или равенство двух снимков.
Второго API-клиента для получения эталона нет; ссылки из отчёта не открываются.

Запросы только читают API. Сетевая граница сравнивается по origin
(схема, host, порт); пути из Link/Location могут выходить за префикс base URL.
Trace обнаруживает чужой origin **после запроса**, а не предотвращает обращение.
Служба допускает такие переходы без токена. Поэтому этот набор не обеспечивает
изоляцию произвольного API с внешними Link/Location; такой сервер требует
отдельного согласования сетевого ограничения ТЗ. Проверки межorigin-переходов
остались в Go. Приёмочные управляемые API используют только свой origin.

Для повторения приёмки без отдельного сервера есть необязательный помощник:

```text
python -m api_tests.verify_live
python -m api_tests.verify_live --full
```

Он временно поднимает три API: пустой, постраничный с PR/повторами/старыми issue
и API, меняющий выдачу между запусками. Обычные live-тесты получают только URL,
список репозиториев и синтетический токен; подготовленные issue им неизвестны.
`--full` дополнительно выполняет mock-группу один раз вместе с постраничным API.
Нужны тот же `GHREPORT_BIN` и pytest; постоянный сервер, Docker и внешняя сеть
не требуются. Унаследованные API URL и токен заменяются настройками помощника.

Запуск отдельной проверки или подробный отчёт:

```text
python -m pytest api_tests/mock/test_cli.py -q
python -m pytest api_tests/mock/test_files.py -q
python -m pytest api_tests/mock/test_collection.py -q
python -m pytest api_tests/mock/test_errors.py -q
python -m pytest api_tests/mock/test_cache.py -q
python -m pytest api_tests/mock/test_retries.py -q
python -m pytest api_tests/mock/test_redirects.py -q
python -m pytest api_tests/mock/test_sequential.py -q
python -m pytest api_tests/test_checks.py -q
python -m pytest api_tests -v --durations=10
```

Таймаут обычного mock-процесса — 10 секунд; проверка исчерпания 5xx использует
15 секунд с учётом настоящих пауз 1/2/4; live-процесса — 120 секунд.
При превышении процесс завершается
и дожидается, тест падает; частичный вывод и credentials не печатаются помощником.
Обработчики и сокеты сервера очищаются в финализаторе, в том числе после ошибки
утверждения. Ошибки серверного потока передаются pytest и не скрываются.
Общего внутреннего бюджета времени и автоматических повторов тестов нет.
Для отключения служебного кэша самого pytest можно добавить `-p no:cacheprovider`;
это не влияет на отдельные временные кэши ghreport.

На Windows POSIX-проверка `symlink/..` пропускается явно; на Linux она обязана
выполняться. Hard link пропускается только при отсутствии поддержки/доступа
файловой системы. В проверенном окружении Windows проходит 74 mock-случая с одним
POSIX-пропуском, Linux — все 75. Полный mock-прогон занимает примерно 15–20 секунд;
тесты не сокращают паузы службы ради скорости.

Последовательность из §4.4 отдельно проверяет `test_sequential.py`: сервер
отправляет заголовки и всё JSON-тело, кроме последнего байта, затем до одной секунды
ждёт появления второго запроса. Второй запрос в этом окне означает провал;
после ожидания тело завершается и проверяются оба результата и trace. Это
ограниченное наблюдение через Event, без sleep; первый ответ освобождается и при
обнаружении перекрытия. Старый max_active_handlers по-прежнему измеряет только
перекрытие подготовки ответов. Конечное окно не доказывает отсутствие любой
возможной отложенной параллельности; тест отклоняет проверенную временную копию
службы со вторым запросом после первых заголовков, до чтения первого тела.

## Структура и перенос из Go

- `helpers/runner.py` — запуск процесса, окружение и захват результата.
- `helpers/server.py` — многопоточный HTTP-сервер и журнал запросов.
- `helpers/checks.py` — независимые проверки JSON, отчёта, RFC3339 и JSON Lines;
  точные дроби времени, UTC-смещения и сопоставление trace с журналом сервера.
- Общий `conftest.py` — бинарник, временные пути и фикстура запуска.
- `mock/conftest.py` — фабрика серверов с очисткой и синтетический токен.
- `mock/test_cli.py` — девять вариантов ошибочной конфигурации.
- `mock/test_files.py` — 18 случаев отчёта, конфликтов путей, локальных отказов,
  отражённого токена и совмещения файлового out с кэшем, повторами и частичным отказом.
- `mock/test_collection.py` — пять сценариев пагинации, отбора, порядка и циклов.
- `mock/test_errors.py` — 19 случаев: ошибки первой/следующей страницы без повторов,
  продолжение сбора, несколько ошибок при частичном успехе, unauthorized/all_failed
  с stdout и файловым out, сохранением старого отчёта и trace.
- `mock/test_cache.py` — семь случаев: страницы/301 между процессами, обновление
  ETag/Link и их сброс, повреждённые JSON/ETag, сохранность кэша при 5xx/401/invalid JSON.
- `mock/test_redirects.py` — 11 случаев: 301/302/307, относительная пагинация,
  валидаторы по своим URL и конечные отказы перенаправлений.
- `mock/test_retries.py` — пять случаев: реальный Retry-After, исчерпание 403/429,
  восстановление после 500 и оборванного тела с сохранением статуса 200 в trace.
- `mock/test_sequential.py` — последовательность при незавершённом теле ответа.
- `test_checks.py` — 10 узких регрессий валидаторов: Authorization с JSON-экранированием,
  вложенными объектами/массивами и разным регистром; диапазоны смещений RFC3339,
  допустимые границы и сохранение наносекунд.
- `live/conftest.py` — явные настройки API и запуск через общий помощник.
- `live/test_api.py` — два независимых случая свойств неизвестной выдачи.
- `verify_live.py` — необязательная воспроизводимая проверка live-группы
  с разными временными API через её обычный интерфейс настроек.

Полнота неизвестной выдачи не доказывается по одному отчёту: PR без маркера,
скрытая страница без Link и пропущенный элемент требуют управляемых данных.
Обязательные 304 и равенство отчётов также проверяются в mock, где данные стабильны.

Итоговый прогон с настроенным временным постраничным API:

- Windows, Python 3.14.2 / pytest 9.1.1 / Go 1.27.2: **86 passed, 1 skipped,
  17.68 s**; пропуск относится к POSIX symlink/.. .
- Linux, Python 3.10.22 / pytest 7.4.4 / Go 1.22.12: **87 passed, 15.92 s**,
  без пропусков; контейнер запускался с `--network none`.
- На каждой ОС дополнительно по два live-случая прошли с пустой и меняющейся
  выдачей. Отдельного предоставленного API для прогона не было.
- Проверены отсутствие настроек, ошибочная/частичная настройка, изоляция mock,
  провал live при 401/404/невалидном JSON/необоснованном 304. Временные копии службы
  с обратной сортировкой, отключённым since и чужим origin в trace отклонены.
- После ревью новые регрессии отклонили прежние валидаторы (5 failed, 5 passed);
  исправленный вариант прошёл все 10 случаев. Нарушение последовательности
  во временной Go-копии отклонено на Windows и Linux. Рабочий код службы не менялся.

Измеренный полный прогон существенно короче 10 минут. Число live-запусков
фиксировано (два), число HTTP-страниц неизвестного API заранее не ограничивается.
Слишком долгий Retry-After или выдача без подходящих issue могут привести
к таймауту; это ошибка прогона, а не успешный пропуск. Внешний общий предел
при необходимости задаёт вызывающее окружение, внутреннего счётчика бюджета нет.

После проверки Python-эквивалентов на Windows и Linux удалены
`TestCLI/InvalidArguments`, `TestCLI/Report`, `TestAPIClientRequestAndPage`,
`TestCLI/CollectionAndErrors`, `TestCollectIssuesPaginationAndSelection`,
`TestCollectIssuesCycleAndEarlyStop` и сценарий invalid JSON из ResilienceAndTrace.
Завершён перенос всех групп TestCLI, TestConditionalPageUpdates,
TestCachedRedirectKeepsValidatorsAtTheirURL, обычных redirect-сценариев и
TestAPIClientErrors. Их Go-дубликаты и ненужная сборка process-бинарника удалены.
Из TestCacheDoesNotMaskFailures сохранён отдельный TestCacheDoesNotMaskNetworkFailure
с искусственной транспортной ошибкой. Проверки сериализации TestReportJSONContract
и TestFatalReportJSONContract также заменены внешними проверками отчётов.
Матрица сохранённых утверждений находится в плане. TestOutputFailures,
TestReportContainsToken, таблицы разбора/валидации, подменённые часы/транспорт,
межorigin-проверки и TestDockerImage сохраняются. Полный одинаковый интеграционный
набор на двух языках не поддерживается.

## Проверка в Linux

При наличии Go и Python в Linux, из корня репозитория:

```bash
go -C service build -o /tmp/ghreport .
export GHREPORT_BIN=/tmp/ghreport
python -m pip install -r api_tests/requirements.txt
python -m pytest api_tests/mock -q
```

Для Docker можно подготовить отдельный тестовый образ. Зависимости загружаются
при подготовке; сам mock-прогон выполняется с `--network none`. Производственный
`service/Dockerfile` не меняется. Пример PowerShell из корня репозитория:

```powershell
$testDockerfile = Join-Path $env:TEMP 'ghreport-api-tests.Dockerfile'
@'
FROM golang:1.22.12-bookworm AS build
WORKDIR /src
COPY go.mod *.go ./
RUN CGO_ENABLED=0 go build -o /ghreport .
FROM python:3.10-slim-bookworm
RUN python -m pip install --no-cache-dir pytest==7.4.4
COPY --from=build /ghreport /usr/local/bin/ghreport
ENV GHREPORT_BIN=/usr/local/bin/ghreport PYTHONDONTWRITEBYTECODE=1
WORKDIR /repo
'@ | Set-Content -LiteralPath $testDockerfile -Encoding utf8
docker build -f $testDockerfile -t ghreport-api-tests-stage1 service/
$testsPath = (Resolve-Path 'api_tests').Path
docker run --rm --network none --mount "type=bind,source=$testsPath,target=/repo/api_tests,readonly" ghreport-api-tests-stage1 python -m pytest api_tests/mock -q -p no:cacheprovider
# Полный набор с временными API, включая live, без внешней сети:
docker run --rm --network none --mount "type=bind,source=$testsPath,target=/repo/api_tests,readonly" ghreport-api-tests-stage1 python -m api_tests.verify_live --full
```

Pytest внутри контейнера запускает `/usr/local/bin/ghreport` как обычный процесс.
Это проверка Linux-бинарника, а не запуск финального scratch-образа ghreport.
Его свойства по-прежнему проверяет отдельный `TestDockerImage` из Go-набора.
