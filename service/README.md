# ghreport

Консольная программа на Go для отчёта по issue репозиториев GitHub.
Спецификация: [task23_go_python.md](../docs/task23_go_python.md).
Порядок разработки: [PLAN_task2.md](../docs/PLAN_task2.md).

## Возможности

Работает сбор страниц списка issue и JSON-отчёт в stdout или файл.
Запросы репозиториев и страниц выполняются последовательно.
Отчёт содержит все поля схемы ТЗ, UTC generated_at, исходный created_at,
порядок labels из API и пустые массивы вместо null.

Адреса следующих страниц берутся из rel="next" в Link и не конструируются.
PR исключаются по наличию ключа pull_request, в том числе со значением null.
Фильтр --since включителен и сравнивает дату создания с 00:00:00 UTC.
Повторы number внутри репозитория удаляются, сохраняется первая подходящая
запись. --limit ограничивает число подходящих уникальных issue; после его
достижения следующая страница не запрашивается. Выбранные issue сортируются
по моменту created_at, затем по number. Репозитории сохраняют порядок --repos.

Реализованы перенаправления, повторы, обработка rate limit и HTTP trace.
ETag-кэш страниц и постоянные перенаправления сохраняются между запусками.
Go-служба и Docker-образ реализованы и проверены на Windows и Linux.
Python-набор завершён: 75 управляемых случаев, два случая свойств неизвестного
API и 10 регрессий общих валидаторов, с приёмкой на Windows и Linux.
Воспроизведение полной проверки с временными
API: `python -m api_tests.verify_live --full` из корня с заданным GHREPORT_BIN.
В Python перенесены процессные сценарии CLI, отчёта, сбора, ошибок,
кэша, повторов, перенаправлений, trace и файловых регрессий. Они проверяются
через GHREPORT_BIN в [api_tests](../api_tests/README.md). В Go остаются
целевые проверки логики, подменяемых ошибок и отдельная проверка Docker-образа.

Обрабатываются 401 (unauthorized), 404 (not_found), исчерпание лимита повторов
rate limit (rate_limited), сетевые ошибки и 5xx после повторов (request_failed)
и непригодный JSON (invalid_response).
При ошибках всех репозиториев выводится all_failed; при частичном успехе —
отчёт с ошибками репозиториев. Ошибка последующей страницы отбрасывает всю
выборку этого репозитория: count=0 и issues=[]. Ответ 401 прекращает весь запуск,
в том числе после успешной обработки предыдущих репозиториев. Цикл страниц,
ошибочный Link и необоснованный 304 считаются invalid_response.
Обычные 403/422 дают request_failed без повторов.

Коды завершения: 0 — все репозитории успешны, 1 — частичный успех,
2 — ошибка конфигурации, 3 — unauthorized, all_failed или локальная ошибка
ввода-вывода. Успешный репозиторий без подходящих issue считается успехом.

Файловые --out и --trace должны указывать на разные файлы. Совпадение, включая
относительные варианты пути и существующие жёсткие ссылки, даёт код 2
до HTTP-запросов и создания файлов или кэша. Существующие файлы сохраняются.
Для проверки также разрешаются символьные ссылки и пути к ещё не созданным
файлам. Ошибка файловой системы при проверке путей даёт код 3 с безопасной
диагностикой.
На Linux символьные ссылки разрешаются до обработки `..`, включая отсутствующий
конечный файл; проверка сравнивает фактические назначения исходных путей.

## Архитектура

Служба — одна консольная программа и один Go-пакет, только стандартная
библиотека. GitHub SDK и внешние зависимости не используются.

Поток выполнения: CLI и окружение → последовательный сбор репозиториев
и страниц → фильтрация и дедупликация → сортировка → JSON-отчёт.

- config.go проверяет параметры и пути файлов.
- client.go выполняет HTTP и перенаправления; retry.go управляет повторами.
- pagination.go разбирает Link, collect.go отбирает issue.
- cache.go хранит исходные страницы и постоянные перенаправления.
- trace.go записывает JSON Lines, report.go формирует JSON.
- main.go связывает компоненты и определяет код завершения.

HTTP-транспорт, часы, ожидание и открытие файлов подменяются в Go-тестах.
Внешняя проверка использует обычный бинарник и произвольный совместимый API,
без специального тестового режима программы.

## Ручной запуск

Go не ниже 1.22. Команды выполняются из каталога service/.
Быстрый запуск успешного сценария:

```text
go run . --repos cli/cli --limit 20 --out -
```

Для проверки именно кода завершения следует запускать собранный бинарник:
`go run` может возвращать код самого инструмента Go.
В PowerShell бинарник можно разместить вне репозитория:

```powershell
go build -o "$env:TEMP\ghreport.exe" .
& "$env:TEMP\ghreport.exe" --repos cli/cli --limit 20 --out -
```

Для локального или другого совместимого API задайте адрес сервера в окружении
того же процесса. Поддерживаются HTTP, HTTPS, префикс пути и завершающий слеш:

```powershell
$env:GITHUB_API_BASE_URL = 'http://127.0.0.1:8080/api/v3/'
& "$env:TEMP\ghreport.exe" --repos stub/alpha --out -
```

Сервер по указанному адресу должен быть запущен отдельно. Отчёт в файл:
`--out report.json`; при этом stdout остаётся пустым. Фатальные JSON-объекты
выводятся в stdout независимо от --out. Диагностика направляется в stderr.

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| --repos | Обязателен | Список owner/repo через запятую; повторы удаляются. |
| --limit | 100 | Максимальное число подходящих issue на репозиторий, не меньше 1. |
| --since | Не задан | Дата создания не раньше YYYY-MM-DD, начало суток UTC. |
| --out | - | JSON в stdout либо указанный файл. |
| --trace | Не задан | Файл JSON Lines для попыток HTTP. |
| --cache-dir | ./ghreport-cache | Постоянный каталог исходных страниц. |

Пример частичного отчёта (код завершения 1):

```json
{
  "generated_at": "2026-10-25T09:00:00Z",
  "repos": [
    {
      "repo": "stub/alpha", "error": null, "count": 1,
      "issues": [
        {
          "number": 1, "title": "Первый выпуск", "author": "octocat",
          "labels": [], "created_at": "2026-01-05T10:00:00Z",
          "url": "https://example.com/issue/1"
        }
      ]
    },
    {"repo": "stub/missing", "error": "not_found", "count": 0, "issues": []}
  ]
}
```

## Окружение и HTTP

| Переменная | Значение |
| --- | --- |
| GITHUB_API_BASE_URL | По умолчанию https://api.github.com, только если переменная не задана. |
| GITHUB_TOKEN | Необязательный токен; непустое значение передаётся как Authorization: Bearer. |

HTTP-клиент использует стандартную библиотеку Go. Запрашиваются state=open,
sort=created, direction=asc, per_page=100. Заголовки: Accept
application/vnd.github+json, X-GitHub-Api-Version 2026-03-10 и User-Agent
ghreport/1.0, идентифицирующий эту программу. Параметр API since не используется.
Таймаут запроса, включая чтение тела, — 30 секунд. Сырые HTTP-ошибки и тела
ответов об ошибках в диагностику не передаются.
В точке входа отключён стандартный логгер Go: внутренние сообщения net/http
могут содержать необработанные байты сервера, включая отражённый токен.
Диагностика службы и HTTP trace формируются отдельно и продолжают работать;
повторное использование соединений сохраняется.

При разборе created_at поддерживаются строчные t/z и произвольная длина
дробной части секунды. Сортировка учитывает цифры после наносекунд без
округления; конечные нули дроби не меняют момент времени. В отчёт попадает
исходная строка API. Отбор --since по-прежнему использует начало дня UTC.

Для Link поддерживаются абсолютные и относительные адреса, несколько
заголовков, параметры и отношения в разном порядке, значения в кавычках.
Query следующего адреса сохраняется. Пустая страница с next не останавливает
обход. Токен отправляется только исходному origin (схема, хост и порт);
ссылка на другой origin обслуживается без передачи токена этому адресу.

## Повторы и перенаправления

Сетевые ошибки, включая таймаут и ошибку чтения тела, и ответы 5xx получают
до трёх повторов с паузами 1, 2 и 4 секунды.

Rate limit определяется для 403/429 при наличии Retry-After,
X-RateLimit-Remaining: 0 или сообщения об ограничении частоты в теле.
Для него допускаются два повтора. Приоритет паузы: корректный Retry-After
(секунды или HTTP-дата), затем X-RateLimit-Reset (UTC epoch), затем 60 и 120
секунд. Истёкшее время даёт нулевую паузу; некорректный заголовок пропускается
в пользу следующего источника. Указанная сервером пауза не сокращается.
Счётчики сетевых повторов и rate limit не сбрасываются при чередовании ошибок
одного запроса. После исчерпания соответствующего бюджета обработка переходит
к следующему репозиторию. 401, 404 и некорректный JSON не повторяются.

Перенаправления 301/302/307 обрабатываются явно, максимум десять переходов.
301 сохраняется в кэше для следующих запусков; 302/307 — временные.
Цикл и некорректный
Location дают request_failed. Относительный Link после перенаправления
разрешается от конечного URL; токен также передаётся только исходному origin.

HTTP-обмен выполняется через переиспользуемый стандартный http.Transport
и контекст с таймаутом 30 секунд. Это позволяет самостоятельно обрабатывать
Location и сохранять полученный HTTP-статус даже при некорректном адресе перехода.
Тела ответов закрываются до следующей попытки или ожидания.

## Постоянный ETag-кэш

--cache-dir задаёт каталог, по умолчанию ./ghreport-cache. Он создаётся после
валидации конфигурации. Сохраняются исходные страницы API до фильтрации:
можно менять --limit и --since, используя тот же каталог. Стандартный каталог
service/ghreport-cache исключён из Git.

При наличии сохранённого ETag отправляется If-None-Match с тем же значением,
включая кавычки и W/. Ответ 200 после успешного разбора заменяет тело, ETag
и Link. Если новый ответ не содержит ETag, старый валидатор удаляется,
следующий запрос будет безусловным.

Ответ 304 использует сохранённое тело и получает from_cache: true в trace.
Присутствующие ETag и Link обновляют метаданные; отсутствующие сохраняются.
Поэтому 304 без Link не обрывает обход следующих страниц. Без отправленного
ETag и пригодного сохранённого тела ответ 304 считается invalid_response.
Сетевой сбой, 5xx или другой отказ не подменяются устаревшей страницей.

Формат записи — JSON UTF-8, версия 1. Имя файла — SHA-256 полного URL
в шестнадцатеричной записи с расширением .json. Адрес включает схему, хост,
порт, путь и исходный query, что разделяет разные API и страницы.

| Поле | Содержимое |
| --- | --- |
| version | Версия формата, сейчас 1. |
| url | Полный адрес запроса. |
| etag | Сохранённый валидатор; отсутствует при пустом значении. |
| body | Исходный JSON-массив API, включая PR и неизвестные поля; пробелы JSON могут нормализоваться. |
| links | Значения заголовка Link; отсутствует при пустом списке. |
| redirect | Полный адрес назначения постоянного 301; такая запись не содержит body, etag и links. |

Временный файл создаётся в том же каталоге, записывается и закрывается,
затем os.Rename заменяет основную запись. Существующий файл перед заменой
не удаляется. Проверка замены выполнена на Windows; Go не гарантирует
атомарность [Rename](https://pkg.go.dev/os#Rename) на всех платформах.
Одновременная работа нескольких
процессов с одним каталогом кэша не входит в поддерживаемый сценарий.

Повреждённая запись, чужой URL или неизвестная версия формата пропускаются
с безопасной диагностикой; запрос выполняется безусловно. Прочие ошибки
создания, чтения или записи кэша фатальны: код 3, диагностика в stderr,
без успешного отчёта. Ошибка сохранения после HTTP отражается в trace как cache.
ETag проверяется по грамматике entity-tag: кавычки, необязательный префикс W/,
отсутствие управляющих символов и DEL. Непригодный ETag также означает
повреждённую запись и безусловный запрос, без сетевых повторов из-за заголовка.

Заголовки запросов и токен в кэш не записываются. Проверяются также декодированные
JSON-строки, включая Unicode-экранирование, неизвестные поля, вложенные значения,
имена и повторения ключей. При отражении токена запись пропускается с безопасной
диагностикой, а предыдущая запись этого адреса удаляется. При чтении старая
корректная запись с токеном также удаляется с диска; её данные остаются в памяти
для текущего условного запроса и обычной проверки отчёта после 304.
Данные ответа не редактируются; небезопасная запись не сохраняется повторно.
Перед выдачей отчёта его строковые значения дополнительно проверяются на токен,
включая значения из кэша по 304. При обнаружении вывод отменяется целиком:
код 3, безопасная диагностика в stderr, пустой stdout, прежний файл --out
сохраняется. Содержимое полей API не заменяется и не редактируется.

Пример двух запусков с общим каталогом в PowerShell:

```powershell
$cachePath = Join-Path $env:TEMP 'ghreport-manual-cache'
$tracePath = Join-Path $env:TEMP 'ghreport-trace.jsonl'
& "$env:TEMP\ghreport.exe" --repos cli/cli --limit 5 --cache-dir $cachePath --trace $tracePath
& "$env:TEMP\ghreport.exe" --repos cli/cli --limit 5 --cache-dir $cachePath --trace $tracePath
Get-Content -LiteralPath $tracePath -Encoding UTF8
```

Во втором trace ожидаются 304/from_cache: true, если сервер поддерживает
ETag и соответствующие страницы не изменились; изменившаяся страница даст 200.
Сам trace перезаписывается при каждом запуске.

## HTTP trace

--trace задаёт файл JSON Lines: одна строка на каждую попытку, включая
перенаправления и повторы. Файл перезаписывается при каждом запуске.

```powershell
$tracePath = Join-Path $env:TEMP 'ghreport-trace.jsonl'
& "$env:TEMP\ghreport.exe" --repos cli/cli --limit 5 --trace $tracePath --out -
Get-Content -LiteralPath $tracePath -Encoding UTF8
```

Пример строки:

```json
{"ts":"2026-10-24T09:00:00Z","method":"GET","url":"https://api.github.com/repos/cli/cli/issues?direction=asc&per_page=100&sort=created&state=open","status":200,"attempt":1,"from_cache":false,"error":null}
```

attempt начинается с 1 для нового запрашиваемого адреса и увеличивается
при повторах. У адреса перенаправления нумерация начинается заново.
status равен 0 только при отсутствии HTTP-ответа: например, при таймауте
чтения тела после получения заголовков сохраняется статус 200 и error=timeout.
Краткие обозначения ошибок также включают network, rate_limited,
invalid_response, redirect и http_404/http_5xx с фактическим кодом.
from_cache равен true только при использовании сохранённого тела по 304.
Переход по сохранённому 301 не создаёт запись trace, поскольку HTTP-запрос
к исходному адресу не выполняется; запрос к конечному адресу журналируется.

Authorization и тела ошибок не записываются. Если токен буквально встретится
в URL, его значение заменяется на [REDACTED]. Отказ открытия, записи или закрытия
журнала фатален: код 3 и диагностика в stderr, без успешного отчёта.

## Проверки

```text
go test ./...
go test -v -count=1 ./...
gofmt -l .
go vet ./...
```

Go-тесты используют локальный httptest.Server и подменяемый транспорт,
не требуют токена или доступа к публичному GitHub. Группа TestCLI удалена после
переноса утверждений в Python. Регрессии транспортного логгера и экранированного
токена в кэше также перенесены в api_tests после проверки на Windows и Linux;
отдельная сборка бинарника в TestCLITransportDiagnostics удалена. Обычный go test
не запускает Docker.
Таблицы разбора Link и валидации данных сохранены в Go.
Процессные проверки запускаются отдельно по инструкции [api_tests](../api_tests/README.md):
каждый случай имеет свой временный рабочий каталог и кэш.
Проверки выполнены на Windows с Go 1.27.2 и на Linux с Go 1.22.12/1.27.3.
Модульные тесты подменяют HTTP-транспорт, часы и ожидание, поэтому паузы
1/2/4 и 60/120 секунд проверяются без реального ожидания. Python-набор
проверяет настоящий Retry-After: 1, восстановление после сбоев и исчерпание
5xx с настоящими паузами 1/2/4.
Для удаления тестовых каталогов на Windows предусмотрен ограниченный повтор
при временных ошибках доступа, совместного использования и непустого каталога.
Он действует только при очистке ресурсов, не изменяет HTTP-сценарии и не
скрывает ошибку удаления, сохраняющуюся две секунды.

Проверки кэша охватывают замену существующей записи, слабые ETag, обновление
метаданных по 304, ответ без ETag, повреждения и ошибки файловой системы,
разделение адресов разных API и отказ от устаревшего результата при сбое.
В Python отдельные процессы проверяют запуски с общим многостраничным кэшем,
постоянный 301, 304 без Link, другие limit/since, trace и отсутствие токена
в кэше и выводе. Бинарник для них собирается заранее и задаётся через GHREPORT_BIN.

Python-сценарий test_file_report_combines_cache_retry_and_partial_failure
объединяет файловый отчёт, trace, несколько
репозиториев, страницы, фильтрацию, повторы, частичный отказ и кэш между
процессами. Отдельно проверяются конфликты файлов и ошибка открытия отчёта.
В Python фатальные unauthorized/all_failed проверяются вместе с trace,
stdout и файловым --out; прежний файловый отчёт сохраняется.
Ошибки открытия, записи и закрытия отчёта и trace воспроизводятся подменой
единственной внутренней функции открытия; обычный запуск использует os.Create.
Проверяются код 3, безопасная диагностика, закрытие открытых файлов и отказ
от выдачи успешного результата. Запись в stdout также проверяется на отказ.

На Windows подтест символьных ссылок пропускается при отсутствии необходимой
привилегии; на Linux он проверен успешно обеими версиями Go.

## Docker

Команды выполняются из корня репозитория:

```text
docker build -t ghreport service/
docker run --rm ghreport --repos cli/cli --limit 20 --out -
```

Для передачи уже заданного в окружении токена:

```text
docker run --rm -e GITHUB_TOKEN ghreport --repos cli/cli --limit 20 --out -
```

Dockerfile использует Go 1.27.3-bookworm и сборку с CGO_ENABLED=0.
Финальный scratch содержит бинарник, системный набор CA-сертификатов и /work.
Пользователь — 65532:65532; /work принадлежит ему и доступен для записи.
Размер проверенного linux/amd64 образа — около 5,6 МиБ. В нём нет Go
и командной оболочки. Токен и API base URL передаются при запуске.
Контекст сборки допускает только Go-исходники, go.mod и инструкции сборки;
кэши, отчёты, trace, исполняемые файлы и локальные секреты в него не включаются.

Для локального API на хосте Docker Desktop:

```text
docker run --rm -e GITHUB_TOKEN -e GITHUB_API_BASE_URL=http://host.docker.internal:8080/api/v3/ ghreport --repos stub/alpha --out -
```

localhost внутри контейнера относится к самому контейнеру. На Linux-хосте
для такого адреса можно добавить `--add-host host.docker.internal:host-gateway`.

Без монтирования кэш и файлы находятся в рабочем слое контейнера и удаляются
вместе с ним. Для сохранения между отдельными docker run используется volume:

```text
docker volume create ghreport-data
docker run --rm --mount type=volume,source=ghreport-data,target=/work -e GITHUB_TOKEN ghreport --repos cli/cli --limit 20 --trace trace.jsonl --out -
```

Повторите последнюю команду для проверки кэша. Новый volume получает права
рабочего каталога образа; работа с ним проверена от штатного пользователя.
Отчёт и журнал можно сохранить внутри именованного контейнера, затем скопировать:

```powershell
docker create --name ghreport-run --mount type=volume,source=ghreport-data,target=/work -e GITHUB_TOKEN ghreport --repos cli/cli --limit 20 --out report.json --trace trace.jsonl
docker start --attach ghreport-run
docker inspect --format '{{.State.ExitCode}}' ghreport-run
docker cp ghreport-run:/work/report.json "$env:TEMP\ghreport-report.json"
docker cp ghreport-run:/work/trace.jsonl "$env:TEMP\ghreport-trace.jsonl"
docker rm ghreport-run
```

### Проверки в Linux и готового образа

Сборочная стадия позволяет повторить проверки без установки Go на хосте:

```text
docker build --target build -t ghreport-build service/
docker run --rm --network none ghreport-build sh -ec 'go version; test -z "$(gofmt -l .)"; go vet ./...; go test -count=1 ./...'
```

Минимальная версия проверяется отдельно; пример для PowerShell из корня:

```powershell
$source = (Resolve-Path 'service').Path
docker run --rm --network none -e GOTOOLCHAIN=local --mount "type=bind,source=$source,target=/src,readonly" -w /src golang:1.22.12-bookworm sh -ec 'go version; test -z "$(gofmt -l .)"; go vet ./...; go test -count=1 ./...'
```

Оба Go-прогона включают оставшиеся модульные проверки. Настоящий Linux-бинарник
запускает отдельный Python-набор по инструкции api_tests. После подготовки
зависимостей внешняя сеть для mock-прогонов не нужна.

Отдельная проверка финального образа запускается из service/ на хосте
с работающим Docker Engine и доступной сетью между контейнером и хостом:

```powershell
$env:GHREPORT_DOCKER_IMAGE = 'ghreport'
try { go test -run '^TestDockerImage$' -count=1 -v }
finally { Remove-Item Env:GHREPORT_DOCKER_IMAGE -ErrorAction SilentlyContinue }
```

GHREPORT_DOCKER_IMAGE — настройка только Go-теста, программа ghreport её
не читает. Без неё TestDockerImage пропускается, обычный go test не требует
Docker. Тест проверяет пользователя, рабочий каталог, CA, передачу окружения,
два запуска через управляемый API, пагинацию и ETag, файловый вывод и trace,
